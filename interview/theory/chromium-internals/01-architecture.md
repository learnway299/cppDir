 # 01 - Chromium 多进程架构 (Multi-Process Architecture)

## 简介

Chromium 采用多进程架构，将浏览器的不同功能隔离到独立进程中运行。这是 Chromium 最核心的架构决策，直接影响安全性、稳定性和性能。

---

## 1. 为什么要多进程？

### 1.1 单进程浏览器的问题

```
早期浏览器（IE6 等）：单进程，所有标签页在一个进程内

问题：
1. 稳定性 — 一个页面崩溃 → 整个浏览器崩溃
2. 安全性 — 恶意网页可以访问其他页面的数据
3. 性能   — 一个页面卡死 → 所有页面无响应
4. 内存   — 内存泄漏无法释放（进程不结束，泄漏的内存无法回收）
```

### 1.2 多进程的优势

```
Chromium：每个标签页/扩展/插件/GPU 独立进程

优势：
1. 稳定性 — 一个渲染进程崩溃只影响对应标签页，其他不受影响
2. 安全性 — 渲染进程运行在沙箱中，无法直接访问文件系统/网络
3. 性能   — 充分利用多核 CPU，一个页面卡顿不影响其他页面
4. 内存   — 关闭标签页 → 进程结束 → 操作系统回收全部内存
```

## 2. 进程类型

### 2.1 五大核心进程

```
┌──────────────────────────────────────────────────────────────┐
│                    Browser 进程（主进程）                      │
│  - UI 渲染（地址栏、书签栏、前进/后退按钮）                    │
│  - 网络请求（URLRequest）                                     │
│  - 文件访问                                                   │
│  - 进程管理与协调                                             │
│  - 用户输入分发                                               │
└──────┬───────────────┬───────────────┬───────────────┬───────┘
       │               │               │               │
       ▼               ▼               ▼               ▼
┌────────────┐  ┌────────────┐  ┌────────────┐  ┌────────────┐
│ Renderer   │  │ Renderer   │  │    GPU     │  │  Utility   │
│ 进程 (1)   │  │ 进程 (2)   │  │   进程     │  │   进程     │
│            │  │            │  │            │  │            │
│ - HTML解析 │  │ - HTML解析 │  │ - 合成     │  │ - 网络服务 │
│ - CSS计算  │  │ - CSS计算  │  │ - 光栅化   │  │ - 音频服务 │
│ - JS执行   │  │ - JS执行   │  │ - WebGL    │  │ - 解码服务 │
│ - 布局绘制 │  │ - 布局绘制 │  │ - 视频解码 │  │ - 存储服务 │
│ [沙箱]     │  │ [沙箱]     │  │            │  │            │
└────────────┘  └────────────┘  └────────────┘  └────────────┘
```

### 2.2 各进程职责详解

**Browser 进程（特权进程）**：

```
职责：
├── UI 管理 — 地址栏、标签栏、菜单等浏览器 chrome UI
├── 网络层 — 发起和管理所有 HTTP/HTTPS 请求
├── 存储管理 — Cookie、LocalStorage、IndexedDB、Cache
├── 进程生命周期 — 创建/销毁 Renderer/GPU/Utility 进程
├── 权限控制 — 摄像头、麦克风、地理位置等权限弹窗
├── 输入路由 — 将用户输入事件分发到正确的 Renderer 进程
└── 导航控制 — URL 解析、重定向、安全检查

特点：
- 唯一的特权进程，有完整的系统访问权限
- 其他进程都受限（沙箱），必须通过 IPC 请求 Browser 进程代为操作
```

**Renderer 进程（沙箱进程）**：

```
职责：
├── HTML 解析 → DOM 树构建
├── CSS 解析 → 样式计算
├── JavaScript 执行（V8 引擎）
├── 布局计算（Layout）
├── 绘制（Paint）→ 生成绘制指令
└── 合成输入 → 提交给合成线程

特点：
- 运行在严格沙箱中
- 不能直接访问文件系统、网络、硬件
- 每个站点（Site）通常对应一个独立的 Renderer 进程
- 包含多个线程（主线程、合成线程、Worker 线程等）
```

**GPU 进程**：

```
职责：
├── 接收所有进程的 GPU 命令
├── 合成最终画面（Compositor）
├── 光栅化（将绘制指令转为像素）
├── WebGL / WebGPU 渲染
├── 视频硬解码
└── Canvas 2D 加速

特点：
- 全局唯一（所有标签页共享一个 GPU 进程）
- GPU 驱动 bug 是浏览器崩溃的主要来源之一
- GPU 进程崩溃后可以重启，不会丢失数据
```

**Utility 进程**：

```
职责：
├── 网络服务（Network Service）
├── 音频服务（Audio Service）
├── 数据解码（JSON、图片解码等）
├── 存储服务（Storage Service）
└── CDM（Content Decryption Module，DRM 解密）

特点：
- 按需创建和销毁
- 将不安全的操作隔离到独立进程
- Chromium 正在将越来越多的服务从 Browser 进程迁移到 Utility 进程
```

**Plugin 进程（已淘汰）**：

```
历史上用于运行 NPAPI/PPAPI 插件（Flash 等）
Chrome 已移除插件支持，该进程类型不再使用
```

## 3. 进程模型策略

### 3.1 四种进程模型

```
Chromium 支持多种策略（通过命令行参数切换）：

1. Process-per-site-instance（默认）
   - 同一站点的同一实例共享进程
   - 不同站点用不同进程
   - 平衡内存与隔离性

2. Process-per-site
   - 同一站点的所有标签页共享一个进程
   - 更省内存

3. Process-per-tab
   - 每个标签页一个进程
   - 隔离性最好，内存占用最大

4. Single process（调试用）
   - 所有内容在一个进程
   - 仅用于开发调试
```

### 3.2 站点隔离 (Site Isolation)

```
核心安全特性（Chrome 67+ 默认开启）

原则：不同站点（scheme + eTLD+1）的页面必须在不同进程中渲染

例子：
  https://a.example.com  ─┐
  https://b.example.com  ─┤→ 同一站点（example.com），可以共享进程
                          │
  https://evil.com       ─┘→ 不同站点，必须独立进程

解决的问题：
  - Spectre/Meltdown 侧信道攻击：恶意页面无法通过 CPU 漏洞读取其他页面内存
  - 跨站脚本攻击（XSS）的进一步隔离

代价：
  - 内存占用增加 10-20%（更多 Renderer 进程）
  - 跨站 iframe 也需要独立进程（OOPIF - Out-of-Process iframes）
```

### 3.3 OOPIF (Out-of-Process iframes)

```
问题：一个页面内嵌了跨站 iframe

  https://parent.com
  ├── <iframe src="https://child.com">  ← 不同站点
  └── 页面内容

传统做法：iframe 和父页面在同一进程 → 不安全

站点隔离做法：
  Renderer 进程 A（parent.com）
       │
       │ 通过代理 frame 通信
       │
  Renderer 进程 B（child.com）← iframe 在独立进程渲染

挑战：
  - 两个进程的渲染结果需要正确合成到一起
  - 输入事件（点击/滚动）需要正确路由
  - 性能开销（进程间通信）
```

## 4. 沙箱机制 (Sandbox)

### 4.1 沙箱原理

```
目标：即使 Renderer 进程被攻破（如执行恶意 JS），也无法危害系统

Renderer 进程沙箱限制：
├── ❌ 不能直接读写文件系统
├── ❌ 不能直接发起网络请求
├── ❌ 不能访问硬件设备
├── ❌ 不能创建新进程
├── ❌ 不能访问其他进程的内存
└── ✅ 只能通过 IPC 请求 Browser 进程代为操作
```

### 4.2 各平台沙箱实现

| 平台 | 机制 | 说明 |
|------|------|------|
| **Windows** | Restricted Token + Job Object + Desktop | 降低进程权限，限制资源访问 |
| **Linux** | Seccomp-BPF + Namespaces | 限制系统调用，隔离文件系统/网络 |
| **macOS** | Seatbelt (sandbox_init) | App Sandbox 配置文件限制权限 |

### 4.3 沙箱层级

```
                 权限高
                   ▲
                   │
    Browser 进程   │  完整系统权限
                   │
    GPU 进程       │  有限权限（访问 GPU 驱动）
                   │
    Utility 进程   │  按需分配权限
                   │
    Renderer 进程  │  最严格沙箱（几乎无权限）
                   │
                   ▼
                 权限低
```

## 5. 线程模型

### 5.1 Renderer 进程内的线程

```
Renderer 进程
├── Main Thread（主线程）
│   ├── Blink 渲染引擎（DOM/CSS/Layout/Paint）
│   ├── V8 JavaScript 引擎
│   └── 事件处理
│
├── Compositor Thread（合成线程）
│   ├── 接收主线程的绘制结果
│   ├── 处理滚动/缩放（不阻塞主线程）
│   └── 提交帧到 GPU 进程
│
├── Raster Threads（光栅化线程池）
│   └── 将绘制指令转换为位图
│
├── Worker Threads
│   ├── Web Worker
│   ├── Service Worker
│   └── SharedWorker
│
└── IO Thread
    └── 处理 IPC 消息收发
```

### 5.2 为什么主线程是瓶颈？

```
主线程要做的事情：

JS 执行 → DOM 操作 → 样式计算 → 布局 → 绘制 → ... 全部串行

如果 JS 执行 50ms：
├── 样式计算被推迟 50ms
├── 布局被推迟
├── 绘制被推迟
└── 用户感受到卡顿（>16ms 就丢帧）

解决方案：
1. 长任务拆分（requestIdleCallback / scheduler.yield）
2. 将工作移到 Worker 线程
3. 合成线程独立处理滚动/动画（无需等主线程）
```

## 6. 进程间通信 (IPC) 概览

```
Browser ←──── Mojo IPC ────→ Renderer
   │                            │
   │                            │
   ├── Mojo IPC ──→ GPU        │
   │                            │
   └── Mojo IPC ──→ Utility    │

通信方式演进：
1. 旧版：Chrome IPC（基于命名管道/Unix socket）
2. 现代：Mojo（更高效、类型安全、支持跨进程共享内存）

详见 06-mojo-ipc.md
```

## 7. 进程生命周期管理

### 7.1 进程创建

```
1. 用户打开新标签页
2. Browser 进程判断需要哪种 Renderer 进程
   - 已有同站点进程 → 复用
   - 需要新进程 → fork/spawn 新 Renderer
3. 新 Renderer 进程启动，进入沙箱
4. Browser 通过 Mojo 建立通信通道
5. 发送导航指令给 Renderer
```

### 7.2 进程回收

```
内存压力时的回收策略（优先级从低到高）：

1. 后台标签页的 Renderer 进程（最先回收）
   - 用户不可见，回收后重新加载
2. 缓存的进程
3. 当前标签页的子 frame 进程
4. 当前活动标签页（最后才回收）

Android 上更激进：后台标签页的 Renderer 经常被系统杀死
```

## 8. 面试常见问题

**Q1：Chromium 为什么采用多进程架构而不是多线程？**

> 多线程共享地址空间，一个线程的内存错误会影响整个进程；多进程有独立地址空间，互不影响。更关键的是安全——多线程无法做沙箱隔离，恶意代码可以访问进程内所有数据。多进程 + 沙箱才能实现真正的安全隔离。代价是更多内存占用和 IPC 开销。

**Q2：一个 Chrome 浏览器大概有多少个进程？**

> 取决于打开的标签页数和站点数。一般公式：1（Browser）+ N（Renderer，与站点数相关）+ 1（GPU）+ M（Utility）+ 扩展进程。打开 10 个不同站点的标签页，通常有 15-20 个进程。可以通过 `chrome://system` 或任务管理器查看。

**Q3：Renderer 进程中哪些操作在主线程，哪些不在？**

> **主线程**：JS 执行、DOM 操作、样式计算、布局、绘制（生成绘制指令）。
> **合成线程**：合成、滚动处理（无需 JS 参与时）、动画（CSS transform/opacity）。
> **光栅化线程**：将绘制指令转为位图。
> **Worker 线程**：Web Worker 中的 JS。
> 这也是为什么 CSS `transform` 动画比 `top/left` 动画更流畅——前者在合成线程完成，不阻塞主线程。

**Q4：站点隔离解决了什么安全问题？**

> 主要防御 Spectre 侧信道攻击。Spectre 可以利用 CPU 推测执行漏洞，让一个进程读取同进程中其他站点的数据。站点隔离确保不同站点在不同进程，即使利用 Spectre 也读不到跨站数据。

**Q5：为什么 GPU 是独立进程而不是在 Renderer 进程内？**

> 1. GPU 驱动不稳定，独立进程崩溃不影响浏览器和网页。
> 2. 所有 Renderer 共享一个 GPU 进程，避免每个标签页都初始化 GPU 上下文。
> 3. GPU 进程有对硬件的访问权限，不应暴露给沙箱内的 Renderer。

**Q6：Chrome 为什么这么吃内存？**

> 每个进程有独立的地址空间，包含 V8 堆、Blink 堆、共享库映射等。即使空白页面的 Renderer 进程也需要 ~30MB。站点隔离进一步增加了进程数。Chromium 通过以下方式缓解：后台标签页丢弃（Tab Discarding）、进程复用（同站点共享）、PartitionAlloc 内存优化。

**Q7：Browser 进程崩溃和 Renderer 进程崩溃的影响分别是什么？**

> - **Renderer 崩溃**：对应的标签页显示 "Aw, Snap!" 错误页面，其他标签页和浏览器不受影响，用户可以刷新恢复。
> - **Browser 崩溃**：整个浏览器关闭。但 Chrome 有崩溃恢复机制，重启后可以恢复之前的标签页。
> - **GPU 崩溃**：所有页面短暂黑屏，GPU 进程自动重启后恢复渲染。

**Q8：什么是 OOPIF？为什么需要它？**

> Out-of-Process iframes。当页面包含跨站 iframe 时，iframe 在独立 Renderer 进程中渲染。这保证了站点隔离的完整性——即使 iframe 嵌在同一页面中，跨站内容也在不同进程，防止通过 Spectre 等攻击窃取父页面数据。挑战在于跨进程的合成、事件路由和滚动同步。
