# 04 - Prompt 与 Context 工程

## 核心概念

**Context Engineering**：决定模型「这一次看见什么」。比花哨措辞更影响 Coding Agent 成功率。

```
好上下文 = 正确目标 + 硬约束 + 最小充分证据 + 清晰验收
坏上下文 = 空泛需求 + 整库粘贴 + 互相矛盾的规则
```

---

## 原理深入

### 上下文里通常有什么

| 层 | 内容 | 建议 |
|----|------|------|
| 系统 / 产品策略 | 安全、工具协议 | 用户不可随意覆写 |
| 项目规则 | 技术栈、目录约定、禁止事项 | Rules / AGENTS.md / CLAUDE.md |
| 会话记忆 | 当前任务进度 | 定期摘要，防噪声 |
| 检索证据 | 相关文件片段、符号定义 | Top-K，带路径 |
| 动态信号 | 编译错误、测试失败、linter | 原样粘贴，勿改写丢信息 |
| 用户指令 | 本次目标 | 单一主目标，可测 |

### 项目规则文件（业界常见实践）

把「给新人看的 README」浓缩成 **给 Agent 的说明书**：

- 构建命令、测试命令  
- 目录哪里能改 / 不能改  
- 代码风格、错误处理约定  
- 密钥与隐私红线  
- 与本仓库相关的框架版本（Qt 版本、C++ 标准）

价值：减少重复口头约束，降低 Stale knowledge。

### 多文件改动策略

推荐顺序（面试可当标准答法）：

1. **定位**：搜索符号 / 复现路径，列出将改文件  
2. **最小读取**：只读相关头文件与调用点  
3. **小步修改**：一次一个行为变化  
4. **验证**：编译 → 单测 → 相关集成  
5. **再扩面**：确有需要才动相邻模块  

反模式：一上来「重构整个模块」却说不清行为不变式。

### Prompt 模式（够用即可）

| 模式 | 用途 | 注意 |
|------|------|------|
| 角色 + 约束 | 「你是 C++ 审阅者，不改无关文件」 | 约束要可检查 |
| Few-shot | 固定输出格式（如 commit message） | 例子要新、要贴仓库风格 |
| 先计划后动手 | 复杂任务先给步骤 | 计划需用户可改 |
| 反例 | 「不要引入新依赖」 | 比正面清单更防跑偏 |
| 验收清单 | DoD 条目 | 与测试命令绑定 |

Chain-of-Thought：难题可要求简短推理；简单改动不必硬套，浪费 Token。

### Context 不够用时怎么办

| 策略 | 做法 |
|------|------|
| 检索替换 | 用搜索结果换掉无关打开文件 |
| 分治 | 子任务多会话 / 多 PR |
| 摘要 | Runtime 压缩历史工具输出 |
| 外部记忆 | 向量库、issue 链接、设计文档 RAG |
| 升窗 | 换更大 Context 模型（贵，治标） |

### 「给 AI 修 Bug」的优质输入模板

```
现象：
复现步骤：
期望 vs 实际：
环境：OS / 编译器 / 相关模块
已有线索：日志 / 调用栈 / 失败测试名
允许修改范围：路径或模块
不要做：...
验收：如何命令证明修好
```

## 常见面试题

**Q1：Prompt Engineering 和 Context Engineering 差别？**  
答：前者偏「怎么说」；后者偏「让模型看见哪些事实与约束」。Coding 场景 Context 往往更决定成败。

**Q2：为什么要把测试失败原文丢给 Agent？**  
答：错误信息是高密度 Grounding；转述会丢行号与符号，诱发幻觉。

**Q3：Rules 写太长有问题吗？**  
答：有。会挤占任务上下文，且互相冲突时模型随意取舍。应短、可执行、分层（全局 / 目录级）。

**Q4：如何避免 AI 改到无关文件？**  
答：指令写明路径白名单；Review Diff；产品侧限制 write 工具范围；拒绝「大扫除式」重构。

---

## 实战要点

- 一条消息只打一个主目标。  
- 证据优于形容词（「可能是竞态」→ 贴 TSan / 日志时间线）。  
- 规则与文档同源：人看的约定和 Agent 看的约定别两套真相。
