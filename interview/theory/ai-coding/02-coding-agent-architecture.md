# 02 - 编程 Agent 基本架构

## 核心概念

一个典型的 **Coding Agent** 不是「对话框里塞了个大模型」，而是：**客户端负责编辑器与权限，编排层负责任务闭环，模型负责推理与生成，工具面负责触达真实世界（文件系统/终端/浏览器）**。

```
┌──────────────────────────────────────────────────────────┐
│                     客户端 (IDE / CLI)                      │
│  编辑器 Diff │ 终端 │ 会话 UI │ 本地权限/审批 │ 规则文件     │
└─────────────┬────────────────────────────────────────────┘
              │ 任务 / 上下文 / 工具结果
              ▼
┌──────────────────────────────────────────────────────────┐
│                 Agent Runtime（编排层）                      │
│  规划 │ 工具路由 │ 多步循环 │ 停止条件 │ 记忆/摘要          │
└─────────────┬───────────────────────┬────────────────────┘
              │                       │
              ▼                       ▼
     ┌────────────────┐      ┌────────────────────┐
     │  模型服务       │      │  工具面 / MCP        │
     │ 补全/对话/推理  │      │ 读写文件│搜索│Shell │
     │ 流式输出        │      │ 浏览器│工单│自定义   │
     └────────────────┘      └─────────┬──────────┘
                                       │
                              ┌────────▼────────┐
                              │ 代码索引 / Repo  │
                              │ 符号│向量│依赖图 │
                              └─────────────────┘
```

## 原理深入

### 1. 客户端（Client）

职责：

| 能力 | 说明 |
|------|------|
| 上下文采集 | 打开的文件、光标、选区、诊断、Git diff、终端输出 |
| 应用变更 | 展示 Diff、Accept/Reject、多文件补丁 |
| 执行边界 | 哪些命令要确认、工作区沙箱、密钥红线 |
| 人机交互 | 澄清问题、计划确认、中断与回滚 |

CLI Agent（如终端里的 coding agent）与 IDE Agent 差别主要在 **UI 与默认可执行权限**，架构层类似。

### 2. Agent Runtime（编排）

核心循环（业界常称 ReAct 风格：**Reason + Act**）：

```
while not done:
  1. 观察：当前目标、已有证据、上一步工具结果
  2. 决策：再搜？再读？改代码？跑测试？问用户？
  3. 行动：调用工具 / 请求模型生成补丁
  4. 校验：编译、测试、lint；失败则带着日志回到 1
```

关键设计点：

- **停止条件**：测试通过、用户验收、步数/费用上限、重复失败  
- **状态**：任务清单、已改文件、待验证假设  
- **防空转**：同一文件反复无效修改要熔断  

### 3. 模型服务（Model Serving）

| 类型 | 典型用途 |
|------|----------|
| 补全模型 | 行内/块内续写，低延迟 |
| 对话 / 指令模型 | 解释、规划、多文件推理 |
| 推理增强模型 | 难 bug、架构权衡（更慢更贵） |

常见部署：云 API、企业私有化、本机（Ollama 等）。流式输出用于边生成边展示 Diff。

### 4. 工具面（Tools）与 MCP

**Tool Use**：模型输出结构化「要调哪个工具 + 参数」，Runtime 执行后把结果塞回上下文。

**MCP（Model Context Protocol）**：把「工具/数据源」标准化，让 IDE、文档库、浏览器、工单系统以统一方式挂到 Agent 上。面试一句话：**MCP 是 Agent 的「USB 接口」，减少每个工具各写一套集成。**

### 5. 代码索引（Code Intelligence）

没有索引的 Agent ≈ 盲人摸象。常见层次：

1. **全文/正则搜索**（ripgrep）— 快、准字面匹配  
2. **符号/AST**（语言服务、tree-sitter）— 跳定义、找引用  
3. **Embedding 检索** — 语义相似（「登录相关逻辑在哪」）  
4. **Repo map / 依赖图** — 模块关系、影响面  

生产级产品通常 **混合检索**，再把 Top-K 片段交给模型。

### 6. 安全与权限边界

```
高风险：rm -rf、推送密钥、改 CI 密钥、生产库
中风险：写文件、跑测试、装依赖
低风险：只读搜索、解释代码
```

好架构：**默认最小权限 + 危险操作人工确认 + 审计日志**。

### 客户端 ↔ 服务端怎么拆

| 放客户端 | 放服务端/云 |
|----------|-------------|
| 读本地未保存缓冲 | 大模型推理 |
| 应用 Diff、调本地编译器 | 多租户配额、日志策略 |
| 用户密钥不上传（理想） | 索引可云可本地 |
| 审批 UI | Agent 策略与提示词版本 |

面试加分：说明 **「上下文出域」风险** — 打开的文件可能含密钥，客户端应脱敏或禁止上传。

## 常见面试题

**Q1：画一下 Coding Agent 架构并说明数据流。**  
按上图答：用户任务进 Runtime → 检索/读文件 → 模型生成计划或补丁 → 工具执行 → 测试反馈再进入循环 → Diff 回写编辑器。

**Q2：为什么需要索引？全丢进 Context 不行吗？**  
Context 有限且贵；全库塞入会 Lost-in-the-middle，且包含无关噪声。索引负责「只拿相关证据」。

**Q3：MCP 和 Function Calling 什么关系？**  
Function Calling 是模型侧「发起调用」的能力；MCP 是工具侧「如何被发现与接入」的协议。二者配合，不是互斥。

**Q4：多 Agent 有必要吗？**  
简单任务单 Agent 足够。复杂流水线可拆「检索 Agent / 编码 Agent / Review Agent」，代价是协调与成本；面试强调 **先单 Agent + 工具，再谈多 Agent**。

---

## 实战要点

- 评价一个编程 AI：看它 **工具闭环**（能否自己跑测试）而不是文采。  
- 本地大仓库：优先符号搜索 + 明确路径，减少纯语义胡搜。  
- 权限开太大 = 事故；开太小 = Agent 废掉 — 按仓库分级。
