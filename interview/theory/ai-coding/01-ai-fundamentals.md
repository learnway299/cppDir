# 01 - AI 基础概念

## 核心概念

面向工程师的最小概念集：搞清 **模型在干什么、输入输出的计量单位、如何把外部知识接进来、Agent 比聊天多了什么**。

```
用户意图
   │
   ▼
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│ Prompt /    │ ──► │    LLM       │ ──► │ 文本/代码/  │
│ Context     │     │ (补全/推理)   │     │ 工具调用    │
└─────────────┘     └──────────────┘     └─────────────┘
        ▲                                      │
        │         RAG / 工具结果 / 规则          │
        └──────────────────────────────────────┘
```

## 原理深入

### LLM（Large Language Model）

- 本质是在上下文条件下做 **下一个 Token 的概率预测**，不是查数据库，也不是「理解后保证正确」。
- **生成式**：能写代码、解释、规划；也可能 **一本正经地编造**。
- 工程师关心的能力边界：
  - 强：模式匹配、样板代码、改写、根据已有片段续写
  - 弱：无证据的事实、仓库里不存在的 API、复杂全局不变量

### Token / Context Window

| 概念 | 含义 | 工程影响 |
|------|------|----------|
| Token | 模型读写的基本单位（约 ¾ 英文单词 / 1～2 汉字量级，因分词而异） | 计费、延迟、能否塞进整文件 |
| Context Window | 单次请求能看到的最大 Token 数 | 决定「一次能看多少代码」 |
| Temperature | 采样随机性 | 写代码常偏低；头脑风暴可略高 |

Context 满了会发生：截断、摘要丢失、或产品侧自动检索替换 — 详见 [04](04-prompt-context-engineering.md)。

### Prompt / System / User / Tool

常见分层：

1. **System / 开发者指令**：角色、硬性约束、输出格式  
2. **用户消息**：当前任务  
3. **工具结果**：命令输出、文件内容、检索片段  
4. **Few-shot**：正反例，稳定风格与格式  

### RAG（Retrieval-Augmented Generation）

```
问题 → 检索（关键词/向量/符号）→ 相关片段 → 拼进 Prompt → LLM 生成
```

| 对比 | 纯 LLM | RAG |
|------|--------|-----|
| 知识来源 | 训练数据 + 当前上下文 | + 外部文档/代码库 |
| 时效 | 训练截止后易过时 | 可检索最新代码/文档 |
| 幻觉 | 易编造不存在的 API | 可用「必须引用检索结果」约束 |
| 成本 | Context 塞满仓库很贵 | 只塞相关片段 |

**RAG ≠ 微调**：RAG 改的是「这次看到什么」；Fine-tune 改的是「模型权重习惯」。

### Embedding / Vector Search

- Embedding：把文本映射成向量，语义相近则距离近。  
- 用途：文档/代码片段检索、相似 issue、去重。  
- 代码场景常 **混合检索**：向量 + `ripgrep`/符号索引（类名、调用图），比纯向量更稳。

### Agent（相对 Chatbot）

| | Chatbot | Agent |
|---|---------|-------|
| 交互 | 一问一答 | 多步：规划 → 行动 → 观察 → 再规划 |
| 能力 | 主要靠生成 | **Tool Use**（读文件、跑命令、搜代码） |
| 停止 | 用户停止 | 达到目标 / 步数上限 / 需人工批准 |

编程 Agent 典型闭环：**读代码 → 改代码 → 编译/测试 → 根据失败再改**。

### 相关术语辨析

| 术语 | 一句话 |
|------|--------|
| Narrow AI | 特定任务系统（含当前 Coding Agent） |
| AGI | 在广泛任务上接近人类通用能力（尚未达成共识实现） |
| ASI | 超越人类的智能（前瞻概念） |
| Multimodal | 可处理文本以外的输入（图、语音等） |
| Completion vs Chat | 补全模型偏「续写」；对话模型偏指令遵循与工具调用 |
| CoT（Chain-of-Thought） | 让模型先推理再答；费 Token，复杂题有时有用 |

### Fine-tune vs Prompt vs RAG（选型三角）

| 手段 | 适合 | 不适合 |
|------|------|--------|
| Prompt / Rules | 风格、流程、项目约定 | 注入整库私有知识 |
| RAG | 文档/代码库事实、常变知识 | 教模型一种全新推理风格 |
| Fine-tune | 固定领域格式、术语习惯 | 频繁变更的事实；成本高 |

## 常见面试题

**Q1：LLM 会「思考」吗？写代码为什么经常错？**  
答：它在做条件生成，优化的是「像正确答案」，不是形式化验证。缺上下文、训练噪声、目标模糊都会导致错 API、错边界条件。工程上要用工具检索 + 测试验收，而不是相信语气。

**Q2：什么是 RAG？为什么 Coding 场景特别需要？**  
答：先检索再生成。代码库私有、API 易变，模型权重里没有你的仓库；RAG/索引让模型看到真实文件与符号，显著降低幻觉。

**Q3：Agent 和「会调用函数的 Chat」一样吗？**  
答：Tool Use 是 Agent 的必要条件，但 Agent 还强调多步目标、状态、停止条件与错误恢复。单次 function call 更接近增强聊天。

**Q4：AGI 到了吗？面试怎么答？**  
答：当前产品属 Narrow AI / 专用 Agent。AGI 无统一定义与公开达成共识的实现；避免把营销话术当成技术事实。

## 实战要点

- 对 AI 的默认态度：**可疑的高生产力助理**，不是编译器。  
- 优先建立「证据链」：指向具体文件/测试，而不是空口描述。  
- 概念题答完要落到工程：RAG、工具、CI — 详见后续章节。
