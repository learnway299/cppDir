# 05 - 事件系统

## 核心概念

输入、命令、尺寸变化等都被抽象为 **`wxEvent` 派生类**。处理方式两条历史路径：

1. **事件表宏**（经典）：`BEGIN_EVENT_TABLE` + `EVT_BUTTON` …  
2. **Bind API**（3.x 推荐）：`btn->Bind(wxEVT_BUTTON, &MyFrame::OnOk, this);`

```
系统消息 → wx 翻译 → wxEvent
                │
                ▼
        目标窗口处理
                │ 未处理且可传播
                ▼
        父窗口方向冒泡（命令事件等）
```

---

## 原理深入

### 事件类别（面试常分）

| 类型 | 例子 | 传播 |
|------|------|------|
| 命令事件 | 按钮点击、菜单 | 通常向父传播，便于 Frame 统一处理 |
| 窗口事件 | 绘制、尺寸、鼠标 | 多在本窗处理，策略因事件而异 |
| 自定义事件 | 业务通知 | 自己 `wxPostEvent` / `QueueEvent` |

### 事件表 vs Bind

| | 事件表 | Bind |
|---|--------|------|
| 写法 | 宏，编译期映射 | 成员函数、lambda、仿函数 |
| 灵活性 | 较弱 | 动态绑定/解绑强 |
| 类型安全 | 宏易写错 ID | 更好 |
| 老代码 | 大量存在 | 新代码首选 |

`Unbind` 必须与 `Bind` 参数匹配，否则解绑失败——悬空回调的来源之一。

### Skip 与「继续传播」

处理函数里 **`event.Skip()`**：允许后续默认处理或继续传播。忘记 Skip 可能导致原生默认行为丢失（如按键）；乱 Skip 可能导致重复处理——按事件文档决定。

### 自定义事件步骤（口述）

1. 定义事件类型宏/`wxEventTypeTag`  
2. 派生 `wxCommandEvent` 或自有事件类  
3. `wxPostEvent` / `QueueEvent` 投递  
4. `Bind` 到接收者

## 常见面试题

**Q1：为什么推荐 Bind？**  
答：类型更安全、可绑定 lambda、可动态生命周期管理，符合现代 C++。

**Q2：按钮事件为何常在 Frame 里处理？**  
答：命令事件会向父传播，Frame 集中处理菜单/按钮逻辑更清晰。

**Q3：`wxPostEvent` 和直接调用有何不同？**  
答：投递进队列异步派发，适合跨对象解耦与线程回传到 UI 队列（跨线程用 `wxQueueEvent`/`CallAfter`）。

---

## 实战要点

- 对象销毁前 `Unbind`。  
- 避免在事件处理里重入销毁自身窗口（用 `Destroy` + 延后）。  
- ID 冲突是事件表时代经典坑；Bind 到具体实例可减少对全局 ID 的依赖。
