# 05 - 应用层 (Application Layer)

## 简介

应用层提供用户可直接使用的网络服务。

---

## 1. HTTP 协议

### 1.1 HTTP 方法

| 方法 | 用途 | 幂等性 |
|------|------|--------|
| GET | 获取资源 | 是 |
| POST | 提交数据 | 否 |
| PUT | 更新资源（完整） | 是 |
| PATCH | 更新资源（部分） | 否 |
| DELETE | 删除资源 | 是 |

### 1.2 HTTP 状态码

| 范围 | 含义 | 常见 |
|------|------|------|
| 1xx | 信息 | 100 Continue |
| 2xx | 成功 | 200 OK, 201 Created |
| 3xx | 重定向 | 301 永久, 302 临时, 304 未修改 |
| 4xx | 客户端错误 | 400 Bad Request, 401, 403, 404 |
| 5xx | 服务器错误 | 500 Internal, 502, 503, 504 |

### 1.3 HTTP 版本对比

| 特性 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|------|----------|--------|--------|
| 连接 | 持久连接 | 多路复用 | QUIC (UDP) |
| 头部 | 文本 | 二进制压缩 | 二进制压缩 |
| 队头阻塞 | 有 | 应用层无 | 无 |
| 加密 | 可选 | 推荐 TLS | 必须 TLS |

## 2. HTTPS

```
HTTPS = HTTP + TLS

TLS 握手流程（简化）：
1. 客户端发送支持的加密套件
2. 服务器选择套件，发送证书
3. 客户端验证证书
4. 密钥交换（如 ECDHE）
5. 开始加密通信
```

## 3. DNS

**DNS (Domain Name System)**：域名解析。

```
解析 www.example.com：

1. 检查本地缓存
2. 查询本地 DNS 服务器
3. 递归查询：
   根服务器 → .com 服务器 → example.com 权威服务器
4. 返回 IP 地址
```

**DNS 记录类型**：
- A：IPv4 地址
- AAAA：IPv6 地址
- CNAME：别名
- MX：邮件服务器
- TXT：文本信息

---

## 4. WebSocket

**WebSocket**：全双工通信协议。

```
HTTP 握手升级：
GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade

之后使用 WebSocket 帧通信
```

## 5. 面试常见问题

**Q1：GET 和 POST 的区别？**
- GET：参数在 URL，可缓存，幂等
- POST：参数在 body，不可缓存，非幂等

**Q2：HTTPS 如何保证安全？**
- 加密：防止窃听
- 证书：验证身份
- 完整性：防止篡改

**Q3：DNS 解析过程？**
- 本地缓存 → 本地 DNS → 根服务器 → TLD → 权威服务器

**Q4：HTTP 缓存机制？**
- 强缓存：Cache-Control, Expires
- 协商缓存：ETag, Last-Modified

## 6. HTTP 版本演进详解

### 6.1 HTTP/1.0 → HTTP/1.1

```
HTTP/1.0 的问题：
┌─────────────────────────────────────────────────────────────┐
│ 每个请求都需要建立新的 TCP 连接                              │
│                                                             │
│ 客户端                              服务器                   │
│    │ ──── TCP 建立 ─────────────────► │                     │
│    │ ──── GET /page.html ───────────► │                     │
│    │ ◄──── 响应 ────────────────────── │                     │
│    │ ──── TCP 关闭 ─────────────────► │                     │
│    │                                   │                     │
│    │ ──── TCP 建立 ─────────────────► │  每个资源都重复！    │
│    │ ──── GET /style.css ───────────► │                     │
│    │ ◄──── 响应 ────────────────────── │                     │
│    │ ──── TCP 关闭 ─────────────────► │                     │
└─────────────────────────────────────────────────────────────┘

HTTP/1.1 改进：
┌─────────────────────────────────────────────────────────────┐
│ 持久连接 (Keep-Alive)：一个连接发送多个请求                  │
│                                                             │
│ 客户端                              服务器                   │
│    │ ──── TCP 建立 ─────────────────► │                     │
│    │ ──── GET /page.html ───────────► │                     │
│    │ ◄──── 响应 ────────────────────── │                     │
│    │ ──── GET /style.css ───────────► │  复用同一连接       │
│    │ ◄──── 响应 ────────────────────── │                     │
│    │ ──── GET /script.js ───────────► │                     │
│    │ ◄──── 响应 ────────────────────── │                     │
│    │ ──── TCP 关闭 ─────────────────► │                     │
└─────────────────────────────────────────────────────────────┘
```

**HTTP/1.1 主要特性**：

| 特性 | 说明 |
|------|------|
| 持久连接 | 默认 Keep-Alive，减少 TCP 握手开销 |
| 管道化 | 可以不等响应就发送下一个请求（但很少使用） |
| 分块传输 | Transfer-Encoding: chunked |
| Host 头 | 支持虚拟主机 |
| 缓存控制 | Cache-Control 替代 Expires |
| 范围请求 | Range 头支持断点续传 |

**HTTP/1.1 的问题**：

```
队头阻塞 (Head-of-Line Blocking)：
┌─────────────────────────────────────────────────────────────┐
│ 即使管道化，响应也必须按请求顺序返回                         │
│                                                             │
│ 请求：   GET /big.jpg  →  GET /small.css  →  GET /tiny.js   │
│                                                             │
│ 响应：   [====big.jpg====] [css] [js]                       │
│          ↑                                                  │
│          小文件必须等待大文件完成才能返回                    │
└─────────────────────────────────────────────────────────────┘

解决方案（HTTP/1.1 时代）：
- 域名分片：多个域名并行连接（每个域名 6 个连接限制）
- 资源合并：CSS/JS 打包、雪碧图
- 内联资源：Base64 图片
```

### 6.2 HTTP/2 革命性改进

```
HTTP/2 核心：二进制分帧 + 多路复用

┌─────────────────────────────────────────────────────────────┐
│                    单一 TCP 连接                            │
│ ┌─────────────────────────────────────────────────────────┐ │
│ │ Stream 1: GET /page.html                                │ │
│ │   Frame 1 ──► Frame 2 ──► Frame 3 ──►                   │ │
│ │                                                         │ │
│ │ Stream 3: GET /style.css                                │ │
│ │   Frame 1 ──► Frame 2 ──►                               │ │
│ │                                                         │ │
│ │ Stream 5: GET /script.js                                │ │
│ │   Frame 1 ──► Frame 2 ──► Frame 3 ──► Frame 4 ──►       │ │
│ └─────────────────────────────────────────────────────────┘ │
│                                                             │
│ 多个流交错发送，无需等待：                                   │
│ [S1-F1][S3-F1][S5-F1][S1-F2][S3-F2][S5-F2][S1-F3]...       │
└─────────────────────────────────────────────────────────────┘
```

**HTTP/2 主要特性**：

| 特性 | 说明 |
|------|------|
| 二进制分帧 | 请求/响应被拆分为帧，更高效解析 |
| 多路复用 | 单连接并行处理多个请求响应 |
| 头部压缩 | HPACK 算法，静态表 + 动态表 + 哈夫曼编码 |
| 服务器推送 | 服务器主动推送资源 |
| 流优先级 | 指定资源加载优先级 |
| 流量控制 | 流级别和连接级别的流量控制 |

**HPACK 头部压缩**：

```
传统 HTTP/1.1 头部问题：
- 每个请求都发送完整头部
- Cookie、User-Agent 等重复传输
- 头部通常 500-800 字节

HPACK 压缩：
┌─────────────────────────────────────────────────────────────┐
│ 静态表：61 个常用头部预定义                                  │
│   索引 2 = :method: GET                                     │
│   索引 4 = :path: /                                         │
│   索引 7 = :scheme: https                                   │
│                                                             │
│ 动态表：会话中动态添加                                       │
│   [自定义头部: 值] → 后续用索引引用                          │
│                                                             │
│ 哈夫曼编码：高频字符用短码表示                               │
│                                                             │
│ 压缩率：通常 85%-90%                                        │
└─────────────────────────────────────────────────────────────┘
```

**HTTP/2 仍存在的问题**：

```
TCP 层队头阻塞：
┌─────────────────────────────────────────────────────────────┐
│ HTTP/2 多路复用建立在 TCP 之上                              │
│                                                             │
│ TCP 视角：所有帧都是一个有序字节流                           │
│                                                             │
│ 发送：[S1][S3][S5][S1][S3]...                               │
│                  ↑                                          │
│              丢包重传                                        │
│                  ↓                                          │
│ 接收：[S1][S3][  等待  ][S5][S1][S3]...                     │
│                  ↑                                          │
│       所有流都被阻塞，即使 S1、S3 数据已到达                 │
└─────────────────────────────────────────────────────────────┘
```

### 6.3 HTTP/3 与 QUIC

```
HTTP/3：基于 QUIC（UDP）的下一代协议

QUIC 架构：
┌─────────────────────────────────────────────────────────────┐
│                        HTTP/3                               │
├─────────────────────────────────────────────────────────────┤
│                         QUIC                                │
│  ┌─────────────────────────────────────────────────────┐    │
│  │ 多路复用 │ 可靠传输 │ 加密 │ 拥塞控制 │ 连接迁移    │    │
│  └─────────────────────────────────────────────────────┘    │
├─────────────────────────────────────────────────────────────┤
│                         UDP                                 │
├─────────────────────────────────────────────────────────────┤
│                          IP                                 │
└─────────────────────────────────────────────────────────────┘

解决 TCP 队头阻塞：
┌─────────────────────────────────────────────────────────────┐
│ QUIC 流是独立的：                                           │
│                                                             │
│ Stream 1: [帧1][帧2][  丢包  ][帧4] ← 只阻塞 Stream 1       │
│ Stream 3: [帧1][帧2][帧3] ← 正常接收，不受影响              │
│ Stream 5: [帧1][帧2] ← 正常接收，不受影响                   │
└─────────────────────────────────────────────────────────────┘
```

**QUIC 核心特性**：

| 特性 | 说明 |
|------|------|
| 0-RTT 连接 | 复用之前的密钥，首次请求就带数据 |
| 独立流 | 流级别丢包只影响该流 |
| 连接迁移 | 基于连接 ID，IP 变化不断开连接 |
| 内置加密 | 必须 TLS 1.3，握手与加密合并 |
| 用户空间实现 | 不受操作系统限制，易于迭代 |

**连接建立对比**：

```
TCP + TLS 1.2：3 个 RTT
┌────────────────────────────────────────┐
│ RTT 1: TCP SYN/SYN-ACK/ACK             │
│ RTT 2: TLS ClientHello/ServerHello     │
│ RTT 3: TLS 密钥交换/完成               │
│ RTT 4: 发送 HTTP 请求                  │
└────────────────────────────────────────┘

TCP + TLS 1.3：2 个 RTT
┌────────────────────────────────────────┐
│ RTT 1: TCP SYN/SYN-ACK/ACK             │
│ RTT 2: TLS 握手合并完成                │
│ RTT 3: 发送 HTTP 请求                  │
└────────────────────────────────────────┘

QUIC：1 个 RTT（首次），0 个 RTT（复用）
┌────────────────────────────────────────┐
│ 首次连接：                             │
│ RTT 1: QUIC 握手 + TLS + 首个请求      │
│                                        │
│ 复用连接（0-RTT）：                    │
│ RTT 0: 立即发送请求（用缓存的密钥）    │
└────────────────────────────────────────┘
```

## 7. TLS/SSL 深入解析

### 7.1 TLS 版本历史

```
SSL/TLS 演进：

SSL 2.0 (1995) ─► SSL 3.0 (1996) ─► TLS 1.0 (1999)
    ↓                  ↓                  ↓
  已废弃            已废弃             已废弃

TLS 1.1 (2006) ─► TLS 1.2 (2008) ─► TLS 1.3 (2018)
    ↓                  ↓                  ↓
  已废弃            主流使用          推荐使用

安全事件：
- POODLE (2014)：攻破 SSL 3.0
- BEAST (2011)：攻击 TLS 1.0 CBC 模式
- Heartbleed (2014)：OpenSSL 漏洞
```

### 7.2 TLS 1.2 握手详解

```
完整 TLS 1.2 握手流程（RSA 密钥交换）：

客户端                                         服务器
   │                                              │
   │ ─────── ClientHello ────────────────────────►│
   │   - 支持的 TLS 版本                          │
   │   - 支持的密码套件列表                       │
   │   - 随机数 Client Random                     │
   │   - 压缩方法                                 │
   │                                              │
   │ ◄─────── ServerHello ─────────────────────── │
   │   - 选定的 TLS 版本                          │
   │   - 选定的密码套件                           │
   │   - 随机数 Server Random                     │
   │   - Session ID                               │
   │                                              │
   │ ◄─────── Certificate ─────────────────────── │
   │   - 服务器证书链                             │
   │                                              │
   │ ◄─────── ServerKeyExchange（可选）────────── │
   │   - ECDHE/DHE 参数                           │
   │                                              │
   │ ◄─────── CertificateRequest（可选）───────── │
   │   - 请求客户端证书（双向认证）               │
   │                                              │
   │ ◄─────── ServerHelloDone ─────────────────── │
   │                                              │
   │ ─────── ClientKeyExchange ──────────────────►│
   │   - 预主密钥（用服务器公钥加密）             │
   │                                              │
   │ ─────── ChangeCipherSpec ───────────────────►│
   │   - 后续使用协商的密钥加密                   │
   │                                              │
   │ ─────── Finished ───────────────────────────►│
   │   - 握手消息的验证数据                       │
   │                                              │
   │ ◄─────── ChangeCipherSpec ────────────────── │
   │                                              │
   │ ◄─────── Finished ────────────────────────── │
   │                                              │
   │ ════════ 开始加密通信 ═════════════════════  │

密钥派生：
┌─────────────────────────────────────────────────────────────┐
│ 预主密钥 (Pre-Master Secret)                                │
│     │                                                       │
│     ▼                                                       │
│ 主密钥 = PRF(预主密钥, "master secret",                     │
│              Client Random + Server Random)                 │
│     │                                                       │
│     ▼                                                       │
│ 密钥块 = PRF(主密钥, "key expansion",                       │
│              Server Random + Client Random)                 │
│     │                                                       │
│     ├─► client_write_MAC_key                                │
│     ├─► server_write_MAC_key                                │
│     ├─► client_write_key                                    │
│     ├─► server_write_key                                    │
│     ├─► client_write_IV                                     │
│     └─► server_write_IV                                     │
└─────────────────────────────────────────────────────────────┘
```

### 7.3 TLS 1.3 改进

```
TLS 1.3 握手（1-RTT）：

客户端                                         服务器
   │                                              │
   │ ─────── ClientHello ────────────────────────►│
   │   - 支持的密码套件                           │
   │   - 支持的 key_share（ECDHE 公钥）           │
   │   - 随机数                                   │
   │                                              │
   │ ◄─────── ServerHello ─────────────────────── │
   │   - 选定的密码套件                           │
   │   - key_share（服务器 ECDHE 公钥）           │
   │                                              │
   │ ◄─────── {EncryptedExtensions} ────────────  │
   │ ◄─────── {Certificate} ─────────────────── │
   │ ◄─────── {CertificateVerify} ──────────── │  加密
   │ ◄─────── {Finished} ───────────────────── │
   │                                              │
   │ ─────── {Finished} ─────────────────────────►│
   │                                              │
   │ ════════ 应用数据 ══════════════════════════ │


TLS 1.3 主要改进：

┌─────────────────────────────────────────────────────────────┐
│ 1. 减少 RTT                                                 │
│    - 首次连接：1-RTT                                        │
│    - 恢复会话：0-RTT（使用 PSK）                            │
│                                                             │
│ 2. 移除不安全特性                                           │
│    - 移除 RSA 密钥交换（无前向保密）                        │
│    - 移除静态 DH                                            │
│    - 移除 CBC 模式（BEAST 攻击）                            │
│    - 移除 SHA-1、MD5                                        │
│    - 移除压缩                                               │
│                                                             │
│ 3. 密码套件简化                                             │
│    TLS 1.2: 37+ 种套件                                      │
│    TLS 1.3: 5 种套件                                        │
│      - TLS_AES_128_GCM_SHA256                               │
│      - TLS_AES_256_GCM_SHA384                               │
│      - TLS_CHACHA20_POLY1305_SHA256                         │
│      - TLS_AES_128_CCM_SHA256                               │
│      - TLS_AES_128_CCM_8_SHA256                             │
│                                                             │
│ 4. 全程加密                                                 │
│    - 握手消息从 ServerHello 之后开始加密                    │
│    - 证书也被加密传输                                       │
└─────────────────────────────────────────────────────────────┘
```

### 7.4 证书链与验证

```
证书链结构：

┌─────────────────────────────────────────────────────────────┐
│                    根证书 (Root CA)                         │
│              内置于操作系统/浏览器                           │
│                        │                                    │
│                        │ 签发                               │
│                        ▼                                    │
│               中间证书 (Intermediate CA)                    │
│              可能有多级                                     │
│                        │                                    │
│                        │ 签发                               │
│                        ▼                                    │
│               终端实体证书 (End Entity)                     │
│              网站使用的证书                                 │
└─────────────────────────────────────────────────────────────┘

验证过程：
1. 验证证书签名（用上级 CA 公钥）
2. 验证有效期
3. 验证域名匹配
4. 检查吊销状态（CRL 或 OCSP）
5. 检查证书链完整

证书内容（X.509）：
┌─────────────────────────────────────────────────────────────┐
│ Version                 版本号（v3）                        │
│ Serial Number           唯一序列号                          │
│ Signature Algorithm     签名算法（如 sha256WithRSA）        │
│ Issuer                  签发者 DN                           │
│ Validity                有效期（Not Before, Not After）     │
│ Subject                 主体 DN                             │
│ Subject Public Key      公钥                                │
│ Extensions              扩展                                │
│   - Subject Alt Name    备用名称（SAN，多域名）             │
│   - Key Usage           密钥用途                            │
│   - Basic Constraints   基本约束（是否 CA）                 │
│ Signature               CA 的签名                           │
└─────────────────────────────────────────────────────────────┘
```

### 7.5 密码套件详解

```
密码套件命名格式（TLS 1.2）：
TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256

   │      │    │        │   │   │    │
   │      │    │        │   │   │    └── PRF 使用的哈希
   │      │    │        │   │   └────── 模式（GCM = AEAD）
   │      │    │        │   └────────── 密钥长度
   │      │    │        └────────────── 对称加密算法
   │      │    └─────────────────────── 身份认证算法
   │      └──────────────────────────── 密钥交换算法
   └─────────────────────────────────── 协议

密钥交换对比：
┌────────────────────────────────────────────────────────────┐
│ RSA 密钥交换：                                             │
│   客户端生成预主密钥 → 用服务器公钥加密 → 发送             │
│   缺点：无前向保密（服务器私钥泄露，历史通信可解密）       │
│                                                            │
│ ECDHE (Elliptic Curve Diffie-Hellman Ephemeral)：          │
│   双方各生成临时密钥对 → 交换公钥 → 各自计算共享密钥       │
│   优点：每次会话密钥不同，具有前向保密                     │
│                                                            │
│ 前向保密 (Forward Secrecy)：                               │
│   即使长期私钥泄露，过去的通信仍然安全                     │
└────────────────────────────────────────────────────────────┘
```

### 7.6 HTTPS 加密机制详解

#### 7.6.1 对称加密 vs 非对称加密

```
┌─────────────────────────────────────────────────────────────────────┐
│                        对称加密                                     │
├─────────────────────────────────────────────────────────────────────┤
│ 特点：加密和解密使用同一个密钥                                      │
│                                                                     │
│ 加密过程：                                                          │
│   明文 + 密钥 ──► 加密算法 ──► 密文                                 │
│   密文 + 密钥 ──► 解密算法 ──► 明文                                 │
│                                                                     │
│ 常用算法：                                                          │
│   - AES-128/256：当前主流，安全高效                                 │
│   - ChaCha20：移动设备友好，Google 推荐                             │
│   - 3DES：已淘汰                                                    │
│                                                                     │
│ 优点：速度快，适合大量数据加密                                      │
│ 缺点：密钥分发困难（如何安全传递密钥？）                            │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│                       非对称加密                                    │
├─────────────────────────────────────────────────────────────────────┤
│ 特点：使用一对密钥（公钥 + 私钥）                                   │
│   - 公钥加密，私钥解密                                              │
│   - 私钥签名，公钥验证                                              │
│                                                                     │
│ 加密过程：                                                          │
│   明文 + 公钥 ──► 加密算法 ──► 密文                                 │
│   密文 + 私钥 ──► 解密算法 ──► 明文                                 │
│                                                                     │
│ 常用算法：                                                          │
│   - RSA-2048/4096：经典算法，密钥较长                               │
│   - ECDSA：椭圆曲线，密钥短、速度快                                 │
│   - Ed25519：现代椭圆曲线，性能更优                                 │
│                                                                     │
│ 优点：解决密钥分发问题（公钥可公开）                                │
│ 缺点：速度慢（比对称加密慢 100-1000 倍）                            │
└─────────────────────────────────────────────────────────────────────┘

性能对比（加密 1MB 数据）：
┌─────────────┬────────────┬────────────┐
│ 算法        │ 类型       │ 耗时       │
├─────────────┼────────────┼────────────┤
│ AES-256-GCM │ 对称       │ ~1 ms      │
│ RSA-2048    │ 非对称     │ ~100 ms    │
│ ECDH P-256  │ 非对称     │ ~10 ms     │
└─────────────┴────────────┴────────────┘
```

#### 7.6.2 HTTPS 混合加密流程

```
HTTPS 采用混合加密：非对称加密交换密钥 + 对称加密传输数据

完整流程：

客户端                                              服务器
   │                                                   │
   │ ════════════════ 1. TCP 握手 ═══════════════════  │
   │                                                   │
   │ ════════════════ 2. TLS 握手 ═══════════════════  │
   │                                                   │
   │ ─────── ClientHello ────────────────────────────► │
   │   包含：                                          │
   │   - 支持的 TLS 版本                               │
   │   - 支持的密码套件列表                            │
   │   - 客户端随机数 (Client Random)                  │
   │   - ECDHE 临时公钥（TLS 1.3）                     │
   │                                                   │
   │ ◄─────── ServerHello ───────────────────────────  │
   │   包含：                                          │
   │   - 选定的 TLS 版本                               │
   │   - 选定的密码套件                                │
   │   - 服务器随机数 (Server Random)                  │
   │   - ECDHE 临时公钥                                │
   │                                                   │
   │ ◄─────── Certificate ─────────────────────────── │
   │   服务器证书（包含服务器公钥）                    │
   │                                                   │
   │ ◄─────── CertificateVerify ─────────────────────  │
   │   用服务器私钥签名，证明拥有私钥                  │
   │                                                   │
   │                                                   │
   │  ┌─────────────────────────────────────────────┐  │
   │  │ 3. 密钥协商（非对称加密）                   │  │
   │  │                                             │  │
   │  │ ECDHE 密钥交换：                            │  │
   │  │   客户端临时私钥 + 服务器临时公钥           │  │
   │  │          ↓                                  │  │
   │  │   计算出预主密钥 (Pre-Master Secret)        │  │
   │  │          ↓                                  │  │
   │  │   服务器临时私钥 + 客户端临时公钥           │  │
   │  │          ↓                                  │  │
   │  │   计算出相同的预主密钥                      │  │
   │  │                                             │  │
   │  │ 密钥派生：                                  │  │
   │  │   预主密钥 + Client Random + Server Random  │  │
   │  │          ↓ HKDF                             │  │
   │  │   会话密钥（对称密钥）                      │  │
   │  └─────────────────────────────────────────────┘  │
   │                                                   │
   │ ─────── Finished ──────────────────────────────► │
   │ ◄─────── Finished ─────────────────────────────  │
   │                                                   │
   │ ════════════════ 4. 加密通信 ═══════════════════  │
   │                                                   │
   │ ─────── 加密的 HTTP 请求 ──────────────────────► │
   │   使用对称密钥 (AES-GCM) 加密                     │
   │                                                   │
   │ ◄─────── 加密的 HTTP 响应 ────────────────────── │
   │   使用对称密钥 (AES-GCM) 加密                     │
   │                                                   │

密钥层次结构：
┌─────────────────────────────────────────────────────────────────────┐
│ 非对称密钥（长期）                                                  │
│   └── 服务器 RSA/ECDSA 密钥对                                       │
│       用途：身份认证、签名验证                                      │
│                                                                     │
│ 非对称密钥（临时）                                                  │
│   └── ECDHE 临时密钥对                                              │
│       用途：密钥交换，每次会话不同                                  │
│                                                                     │
│ 对称密钥（会话）                                                    │
│   └── AES 会话密钥                                                  │
│       用途：加密实际数据传输                                        │
│       派生：从预主密钥 + 随机数生成                                 │
└─────────────────────────────────────────────────────────────────────┘
```

#### 7.6.3 为什么需要混合加密？

```
┌─────────────────────────────────────────────────────────────────────┐
│ 问题：纯对称加密的密钥分发难题                                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│ 如果只用对称加密：                                                  │
│                                                                     │
│ 客户端                    攻击者                    服务器          │
│    │                        │                        │              │
│    │ ──── 密钥 ────────────►│────────────────────────► │            │
│    │                        │                        │              │
│    │        攻击者截获密钥，可以解密所有通信          │              │
│                                                                     │
│ 密钥必须在网络上传输 → 可能被截获 → 不安全                          │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│ 问题：纯非对称加密的性能问题                                        │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│ 如果只用非对称加密：                                                │
│                                                                     │
│ 加密 1MB 数据：                                                     │
│   - 对称加密：~1 ms                                                 │
│   - 非对称加密：~100 ms                                             │
│                                                                     │
│ 网页加载通常需要传输 MB 级别数据                                    │
│ 纯非对称加密会导致严重性能问题                                      │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│ 解决方案：混合加密                                                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│ 1. 使用非对称加密交换对称密钥                                       │
│    - 只需要加密少量数据（密钥本身）                                 │
│    - 安全：密钥不在网络上明文传输                                   │
│                                                                     │
│ 2. 使用对称密钥加密实际数据                                         │
│    - 高效：适合大量数据                                             │
│    - 安全：对称密钥只有双方知道                                     │
│                                                                     │
│ 结合两者优点：安全 + 高效                                           │
└─────────────────────────────────────────────────────────────────────┘
```

### 7.7 HTTPS 安全防护机制

#### 7.7.1 防止窃听（机密性）

```
攻击场景：中间人窃听通信内容

┌─────────────────────────────────────────────────────────────────────┐
│ HTTP（明文传输）：                                                  │
│                                                                     │
│ 客户端                    攻击者                    服务器          │
│    │                        │                        │              │
│    │ ── GET /login ────────►│────────────────────────► │            │
│    │    user=admin          │ ← 攻击者可以看到        │              │
│    │    pass=123456         │   所有明文内容          │              │
│    │                        │                        │              │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│ HTTPS（加密传输）：                                                 │
│                                                                     │
│ 客户端                    攻击者                    服务器          │
│    │                        │                        │              │
│    │ ── [加密数据] ────────►│────────────────────────► │            │
│    │    0x7f3a2b...         │ ← 攻击者只能看到        │              │
│    │                        │   无意义的密文          │              │
│    │                        │   无法解密（没有密钥）  │              │
│                                                                     │
│ 防护机制：                                                          │
│   - 对称加密（AES-GCM）保护数据内容                                 │
│   - 密钥通过安全的密钥交换（ECDHE）协商                             │
│   - 即使截获密文，没有密钥也无法解密                                │
└─────────────────────────────────────────────────────────────────────┘
```

#### 7.7.2 防止篡改（完整性）

```
攻击场景：中间人修改通信内容

┌─────────────────────────────────────────────────────────────────────┐
│ HTTP（无完整性保护）：                                              │
│                                                                     │
│ 客户端                    攻击者                    服务器          │
│    │                        │                        │              │
│    │ ── 转账 100 元 ───────►│                        │              │
│    │                        │ 修改为：转账 10000 元  │              │
│    │                        │────────────────────────► │            │
│    │                        │                        │              │
│    │        篡改成功，服务器无法察觉                 │              │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│ HTTPS 完整性保护机制：                                              │
│                                                                     │
│ 1. 消息认证码 (MAC / AEAD)                                          │
│                                                                     │
│    发送方：                                                         │
│    ┌─────────────────────────────────────────────────┐              │
│    │ 明文 + 密钥 ──► HMAC ──► 认证标签 (Tag)         │              │
│    │ 明文 + 认证标签 ──► 加密 ──► 密文               │              │
│    └─────────────────────────────────────────────────┘              │
│                                                                     │
│    接收方：                                                         │
│    ┌─────────────────────────────────────────────────┐              │
│    │ 密文 ──► 解密 ──► 明文 + 认证标签               │              │
│    │ 明文 + 密钥 ──► HMAC ──► 计算标签               │              │
│    │ 计算标签 vs 收到标签 ──► 匹配则未被篡改         │              │
│    └─────────────────────────────────────────────────┘              │
│                                                                     │
│ 2. AEAD 模式 (Authenticated Encryption with Associated Data)       │
│                                                                     │
│    AES-GCM = AES (加密) + GMAC (认证)                               │
│    - 一次操作同时完成加密和认证                                     │
│    - 任何篡改都会导致认证失败                                       │
│                                                                     │
│ 攻击失败：                                                          │
│ 客户端                    攻击者                    服务器          │
│    │                        │                        │              │
│    │ ── [加密+MAC] ────────►│                        │              │
│    │                        │ 尝试篡改密文           │              │
│    │                        │────────────────────────► │            │
│    │                        │                        │              │
│    │                        │   MAC 验证失败！       │              │
│    │                        │   连接终止             │              │
└─────────────────────────────────────────────────────────────────────┘
```

#### 7.7.3 防止伪装（身份认证）

```
攻击场景：中间人冒充服务器

┌─────────────────────────────────────────────────────────────────────┐
│ 没有身份认证时：                                                    │
│                                                                     │
│ 客户端              攻击者（伪装）              真实服务器          │
│    │                     │                         │                │
│    │ ── 连接请求 ───────►│                         │                │
│    │                     │                         │                │
│    │ ◄── 假证书 ─────────│                         │                │
│    │                     │                         │                │
│    │ ── 敏感数据 ───────►│                         │                │
│    │     (密码等)        │ ← 攻击者获取敏感信息    │                │
│    │                     │                         │                │
│    │         用户以为在和真实服务器通信            │                │
└─────────────────────────────────────────────────────────────────────┘

HTTPS 身份认证机制：

┌─────────────────────────────────────────────────────────────────────┐
│ 1. 数字证书 (Digital Certificate)                                   │
│                                                                     │
│    证书内容：                                                       │
│    ┌───────────────────────────────────────────┐                    │
│    │ Subject: www.example.com                  │ ← 域名             │
│    │ Subject Public Key: [公钥]                │ ← 服务器公钥       │
│    │ Issuer: DigiCert CA                       │ ← 签发机构         │
│    │ Validity: 2024-01-01 ~ 2025-01-01        │ ← 有效期           │
│    │ Signature: [CA 的数字签名]                │ ← 防伪造           │
│    └───────────────────────────────────────────┘                    │
│                                                                     │
│ 2. 证书链验证                                                       │
│                                                                     │
│    ┌─────────────────┐                                              │
│    │ 根证书 (Root CA) │ ← 内置于操作系统/浏览器，绝对信任           │
│    └────────┬────────┘                                              │
│             │ 签发                                                  │
│    ┌────────▼────────┐                                              │
│    │ 中间证书 (ICA)   │                                              │
│    └────────┬────────┘                                              │
│             │ 签发                                                  │
│    ┌────────▼────────┐                                              │
│    │ 服务器证书      │ ← 网站使用的证书                             │
│    └─────────────────┘                                              │
│                                                                     │
│    验证过程：                                                       │
│    a. 用中间 CA 公钥验证服务器证书签名                              │
│    b. 用根 CA 公钥验证中间 CA 证书签名                              │
│    c. 根 CA 证书是预置信任的                                        │
│    d. 全部验证通过 → 证书可信                                       │
│                                                                     │
│ 3. 证书签名验证原理                                                 │
│                                                                     │
│    CA 签发证书时：                                                  │
│    ┌─────────────────────────────────────────────┐                  │
│    │ 证书内容 ──► Hash ──► 摘要                  │                  │
│    │ 摘要 + CA私钥 ──► 签名算法 ──► 数字签名     │                  │
│    └─────────────────────────────────────────────┘                  │
│                                                                     │
│    客户端验证时：                                                   │
│    ┌─────────────────────────────────────────────┐                  │
│    │ 证书内容 ──► Hash ──► 摘要 A                │                  │
│    │ 数字签名 + CA公钥 ──► 解密 ──► 摘要 B       │                  │
│    │ 摘要 A == 摘要 B ？ ──► 是则证书未被篡改    │                  │
│    └─────────────────────────────────────────────┘                  │
└─────────────────────────────────────────────────────────────────────┘

攻击者伪造证书会失败：
┌─────────────────────────────────────────────────────────────────────┐
│ 攻击者尝试伪造 www.example.com 证书：                               │
│                                                                     │
│ 方案1：自己签发证书                                                 │
│   → 证书链无法追溯到受信任的根 CA                                   │
│   → 浏览器拒绝，显示安全警告                                        │
│                                                                     │
│ 方案2：修改真实证书                                                 │
│   → 证书签名验证失败（签名是用 CA 私钥生成的）                      │
│   → 攻击者没有 CA 私钥，无法伪造有效签名                            │
│                                                                     │
│ 方案3：申请合法证书                                                 │
│   → CA 会验证域名所有权（DNS/HTTP 验证）                            │
│   → 攻击者无法证明拥有 www.example.com                              │
│                                                                     │
│ 结论：没有 CA 私钥或域名控制权，无法伪造有效证书                    │
└─────────────────────────────────────────────────────────────────────┘
```

#### 7.7.4 中间人攻击 (MITM) 全面防护

```
中间人攻击场景：

┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│ 客户端 ◄────────► 攻击者 ◄────────► 服务器                          │
│                     │                                               │
│          攻击者位于通信链路中间                                     │
│          可以窃听、篡改、伪装                                       │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

HTTPS 对 MITM 的全面防护：

┌─────────────────────────────────────────────────────────────────────┐
│ 攻击类型          │ 防护机制                                        │
├───────────────────┼─────────────────────────────────────────────────┤
│ 窃听              │ 对称加密 (AES-GCM)                              │
│                   │ 没有密钥无法解密                                │
├───────────────────┼─────────────────────────────────────────────────┤
│ 篡改              │ 消息认证码 (AEAD/MAC)                           │
│                   │ 任何修改导致认证失败                            │
├───────────────────┼─────────────────────────────────────────────────┤
│ 伪装服务器        │ 数字证书 + CA 签名验证                          │
│                   │ 无法伪造有效证书                                │
├───────────────────┼─────────────────────────────────────────────────┤
│ 重放攻击          │ 随机数 + 序列号                                 │
│                   │ 每条消息有唯一标识                              │
├───────────────────┼─────────────────────────────────────────────────┤
│ 降级攻击          │ TLS 版本协商保护                                │
│                   │ HSTS 强制 HTTPS                                 │
├───────────────────┼─────────────────────────────────────────────────┤
│ 密钥泄露后解密    │ 前向保密 (ECDHE)                                │
│                   │ 临时密钥，会话独立                              │
└─────────────────────────────────────────────────────────────────────┘

SSL Stripping 攻击与防护：

┌─────────────────────────────────────────────────────────────────────┐
│ 攻击过程：                                                          │
│                                                                     │
│ 客户端                    攻击者                    服务器          │
│    │                        │                        │              │
│    │ ── HTTP 请求 ─────────►│                        │              │
│    │    (用户输入网址       │                        │              │
│    │     没写 https://)     │                        │              │
│    │                        │ ── HTTPS ─────────────►│              │
│    │                        │                        │              │
│    │ ◄── HTTP 响应 ─────────│◄── HTTPS 响应 ─────────│              │
│    │                        │                        │              │
│    │     攻击者与服务器用 HTTPS                      │              │
│    │     攻击者与客户端用 HTTP（明文）               │              │
│                                                                     │
│ 防护：HSTS (HTTP Strict Transport Security)                         │
│                                                                     │
│ Strict-Transport-Security: max-age=31536000; includeSubDomains      │
│                                                                     │
│ 效果：                                                              │
│   - 浏览器记住该域名必须使用 HTTPS                                  │
│   - 自动将 HTTP 转为 HTTPS（不发出 HTTP 请求）                      │
│   - HSTS Preload List：域名预置在浏览器中                           │
└─────────────────────────────────────────────────────────────────────┘
```

#### 7.7.5 证书安全增强

```
证书透明度 (Certificate Transparency, CT)：

┌─────────────────────────────────────────────────────────────────────┐
│ 问题：CA 可能被入侵或误发证书                                       │
│                                                                     │
│ 2011 年 DigiNotar 事件：                                            │
│   - CA 被入侵，签发了假的 *.google.com 证书                         │
│   - 伊朗用户的 Gmail 流量被监听                                     │
│                                                                     │
│ CT 解决方案：                                                       │
│                                                                     │
│   1. CA 签发证书时，必须提交到公开日志                              │
│   2. 日志服务器返回 SCT (Signed Certificate Timestamp)              │
│   3. 证书必须包含 SCT 才被浏览器信任                                │
│   4. 域名所有者可以监控日志，发现可疑证书                           │
│                                                                     │
│    CA ──► 公开日志 ◄── 监控                                         │
│     │         │         │                                           │
│     └── SCT ──┘         └── 域名所有者                              │
│                                                                     │
│ 浏览器检查：                                                        │
│   Chrome 要求所有证书必须有 CT 记录                                 │
└─────────────────────────────────────────────────────────────────────┘

证书吊销检查：

┌─────────────────────────────────────────────────────────────────────┐
│ 场景：私钥泄露后需要吊销证书                                        │
│                                                                     │
│ 方法 1：CRL (Certificate Revocation List)                           │
│   - CA 定期发布吊销证书列表                                         │
│   - 缺点：列表大，更新慢                                            │
│                                                                     │
│ 方法 2：OCSP (Online Certificate Status Protocol)                   │
│   - 实时查询证书状态                                                │
│   - 缺点：隐私问题（CA 知道你访问了哪些网站）                       │
│                                                                     │
│ 方法 3：OCSP Stapling                                               │
│   - 服务器预先获取 OCSP 响应                                        │
│   - TLS 握手时附带给客户端                                          │
│   - 保护隐私，减少延迟                                              │
│                                                                     │
│ 客户端 ◄── 证书 + OCSP响应 ── 服务器                                │
│                                   │                                 │
│                          预先查询 OCSP                              │
│                                   │                                 │
│                            OCSP 服务器                              │
└─────────────────────────────────────────────────────────────────────┘

证书固定 (Certificate Pinning)：

┌─────────────────────────────────────────────────────────────────────┐
│ 额外安全层：只信任特定证书/公钥                                     │
│                                                                     │
│ 实现方式：                                                          │
│   - HTTP Public Key Pinning (HPKP) - 已废弃                         │
│   - 应用内固定（移动 App）                                          │
│                                                                     │
│ 原理：                                                              │
│   应用预置服务器证书的公钥哈希                                      │
│   连接时验证：实际公钥哈希 == 预置哈希？                            │
│                                                                     │
│ 优点：防止 CA 被入侵后签发假证书                                    │
│ 缺点：证书更换麻烦，配置错误会导致服务不可用                        │
└─────────────────────────────────────────────────────────────────────┘
```

### 7.8 HTTPS 安全面试题

**Q11：HTTPS 如何同时保证安全和性能？**
```
混合加密：
1. 非对称加密（ECDHE）交换密钥
   - 解决密钥分发问题
   - 只用于少量数据（密钥协商）

2. 对称加密（AES-GCM）传输数据
   - 高效，适合大量数据
   - 密钥通过安全方式协商得到
```

**Q12：如何验证网站证书的真实性？**
```
证书链验证：
1. 检查证书签名（用 CA 公钥验证）
2. 检查证书链完整性（一直追溯到根 CA）
3. 检查域名匹配（Subject/SAN）
4. 检查有效期
5. 检查吊销状态（CRL/OCSP）
6. 检查 CT 日志（证书透明度）
```

**Q13：中间人能否替换证书进行攻击？**
```
不能，因为：
1. 攻击者无法获得合法 CA 签名
   - CA 验证域名所有权
   - 攻击者没有目标域名控制权

2. 自签名证书会被拒绝
   - 证书链无法追溯到受信任根 CA
   - 浏览器显示安全警告

3. 修改证书会破坏签名
   - 签名是用 CA 私钥生成的
   - 攻击者没有 CA 私钥
```

**Q14：为什么 HTTPS 能防止重放攻击？**
```
防重放机制：
1. 随机数
   - Client Random + Server Random
   - 每次握手都不同
   - 保证会话密钥唯一

2. 序列号
   - 每条消息有递增序列号
   - 序列号参与 MAC 计算
   - 重放的消息序列号不对

3. 时间戳（TLS 1.3）
   - 0-RTT 数据有时间限制
   - 超时的重放请求被拒绝
```

**Q15：私钥泄露了怎么办？**
```
应对措施：
1. 立即吊销证书
   - 通过 CA 吊销
   - 更新 CRL/OCSP

2. 重新生成密钥对
   - 申请新证书
   - 部署到服务器

3. 历史通信安全评估
   - 如果使用 ECDHE：历史通信仍安全（前向保密）
   - 如果使用 RSA：历史通信可能被解密

最佳实践：
   - 始终使用 ECDHE 等支持前向保密的密钥交换
   - 定期轮换密钥和证书
```

## 8. HTTP 缓存机制详解

### 8.1 强缓存

```
强缓存：不发请求，直接使用缓存

Cache-Control（HTTP/1.1）：
┌─────────────────────────────────────────────────────────────┐
│ max-age=3600        缓存有效期 3600 秒                      │
│ no-cache            必须重新验证                            │
│ no-store            完全不缓存                              │
│ private             仅客户端缓存                            │
│ public              可以被 CDN 等中间缓存                   │
│ immutable           资源永不变化                            │
│ must-revalidate     过期后必须验证                          │
└─────────────────────────────────────────────────────────────┘

Expires（HTTP/1.0）：
Expires: Wed, 21 Oct 2025 07:28:00 GMT
缺点：依赖客户端时间，可能不准确

优先级：Cache-Control > Expires
```

### 8.2 协商缓存

```
协商缓存：发请求验证，可能返回 304

方式一：Last-Modified / If-Modified-Since
┌─────────────────────────────────────────────────────────────┐
│ 首次请求：                                                  │
│   响应头：Last-Modified: Wed, 21 Oct 2025 07:28:00 GMT      │
│                                                             │
│ 再次请求：                                                  │
│   请求头：If-Modified-Since: Wed, 21 Oct 2025 07:28:00 GMT  │
│                                                             │
│ 服务器判断：                                                │
│   未修改 → 304 Not Modified                                 │
│   已修改 → 200 OK + 新内容                                  │
│                                                             │
│ 缺点：                                                      │
│   - 精度只到秒                                              │
│   - 文件修改但内容未变也会失效                              │
└─────────────────────────────────────────────────────────────┘

方式二：ETag / If-None-Match
┌─────────────────────────────────────────────────────────────┐
│ 首次请求：                                                  │
│   响应头：ETag: "5f6a8c3d-1234"                             │
│                                                             │
│ 再次请求：                                                  │
│   请求头：If-None-Match: "5f6a8c3d-1234"                    │
│                                                             │
│ 优点：                                                      │
│   - 内容 hash，精确判断变化                                 │
│   - 不依赖时间                                              │
│                                                             │
│ 优先级：ETag > Last-Modified                                │
└─────────────────────────────────────────────────────────────┘
```

### 8.3 缓存策略实践

```
常见缓存策略：

HTML 文件（入口）：
Cache-Control: no-cache
（每次验证，使用 ETag）

JS/CSS（带 hash）：
Cache-Control: max-age=31536000, immutable
（长期缓存，文件名变化时自动失效）

API 响应：
Cache-Control: private, no-cache
（可能包含用户数据，需要验证）

图片/字体：
Cache-Control: max-age=86400, public
（CDN 缓存一天）
```

## 9. 长连接与短连接

### 9.1 基本概念

```
┌─────────────────────────────────────────────────────────────────────┐
│                          短连接                                     │
├─────────────────────────────────────────────────────────────────────┤
│ 定义：每次请求都建立新连接，完成后立即关闭                          │
│                                                                     │
│ 客户端                                              服务器          │
│    │                                                   │            │
│    │ ══ TCP 建立 ═══════════════════════════════════►  │            │
│    │ ── 请求 1 ─────────────────────────────────────►  │            │
│    │ ◄─ 响应 1 ──────────────────────────────────────  │            │
│    │ ══ TCP 关闭 ═══════════════════════════════════►  │            │
│    │                                                   │            │
│    │ ══ TCP 建立 ═══════════════════════════════════►  │  重复！    │
│    │ ── 请求 2 ─────────────────────────────────────►  │            │
│    │ ◄─ 响应 2 ──────────────────────────────────────  │            │
│    │ ══ TCP 关闭 ═══════════════════════════════════►  │            │
│    │                                                   │            │
│                                                                     │
│ 特点：                                                              │
│   - 每次通信都经历：TCP 握手 → 数据传输 → TCP 挥手                  │
│   - HTTP/1.0 默认行为                                               │
│   - 连接开销大（每次 1.5 RTT 握手 + 2 RTT 挥手）                    │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│                          长连接                                     │
├─────────────────────────────────────────────────────────────────────┤
│ 定义：建立连接后保持，多次请求复用同一连接                          │
│                                                                     │
│ 客户端                                              服务器          │
│    │                                                   │            │
│    │ ══ TCP 建立 ═══════════════════════════════════►  │            │
│    │ ── 请求 1 ─────────────────────────────────────►  │            │
│    │ ◄─ 响应 1 ──────────────────────────────────────  │            │
│    │ ── 请求 2 ─────────────────────────────────────►  │  复用连接  │
│    │ ◄─ 响应 2 ──────────────────────────────────────  │            │
│    │ ── 请求 3 ─────────────────────────────────────►  │            │
│    │ ◄─ 响应 3 ──────────────────────────────────────  │            │
│    │        ...                                        │            │
│    │ ══ TCP 关闭（超时或主动关闭）══════════════════►  │            │
│    │                                                   │            │
│                                                                     │
│ 特点：                                                              │
│   - 一次握手，多次通信                                              │
│   - HTTP/1.1 默认行为（Connection: keep-alive）                     │
│   - 减少 TCP 连接开销                                               │
└─────────────────────────────────────────────────────────────────────┘
```

### 9.2 HTTP 各版本的连接管理

```
┌─────────────────────────────────────────────────────────────────────┐
│                        HTTP/1.0                                     │
├─────────────────────────────────────────────────────────────────────┤
│ 默认：短连接                                                        │
│                                                                     │
│ 开启长连接（非标准扩展）：                                          │
│   请求头：Connection: keep-alive                                    │
│   响应头：Connection: keep-alive                                    │
│                                                                     │
│ 问题：                                                              │
│   - 需要双方都支持                                                  │
│   - 不知道响应何时结束（没有 Content-Length 时）                    │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│                        HTTP/1.1                                     │
├─────────────────────────────────────────────────────────────────────┤
│ 默认：长连接（Keep-Alive）                                          │
│                                                                     │
│ 关闭长连接：                                                        │
│   请求头：Connection: close                                         │
│                                                                     │
│ Keep-Alive 参数：                                                   │
│   Keep-Alive: timeout=5, max=100                                    │
│   - timeout：空闲多久后关闭（秒）                                   │
│   - max：最多复用多少次请求                                         │
│                                                                     │
│ 特性：                                                              │
│   - 管道化（Pipelining）：可连续发送多个请求                        │
│   - 但响应必须按顺序返回（队头阻塞）                                │
│                                                                     │
│ 浏览器限制：                                                        │
│   - 同一域名最多 6 个并发连接                                       │
│   - 需要域名分片来增加并发                                          │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│                        HTTP/2                                       │
├─────────────────────────────────────────────────────────────────────┤
│ 默认：单一长连接 + 多路复用                                         │
│                                                                     │
│ 特点：                                                              │
│   - 一个域名只需要一个 TCP 连接                                     │
│   - 多个请求在同一连接上并行处理                                    │
│   - 无应用层队头阻塞                                                │
│                                                                     │
│ 连接管理：                                                          │
│   - 连接更持久（通常保持更长时间）                                  │
│   - 不需要域名分片                                                  │
│   - 服务器可主动关闭空闲流                                          │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│                        HTTP/3 (QUIC)                                │
├─────────────────────────────────────────────────────────────────────┤
│ 基于 UDP，但仍是长连接概念                                          │
│                                                                     │
│ 特点：                                                              │
│   - 连接迁移：IP 变化不断开连接                                     │
│   - 0-RTT 连接恢复                                                  │
│   - 流级别独立，无队头阻塞                                          │
└─────────────────────────────────────────────────────────────────────┘
```

### 9.3 TCP 层的 Keep-Alive

```
注意：HTTP Keep-Alive ≠ TCP Keep-Alive

┌─────────────────────────────────────────────────────────────────────┐
│                    HTTP Keep-Alive                                  │
├─────────────────────────────────────────────────────────────────────┤
│ 层级：应用层                                                        │
│ 作用：复用 TCP 连接发送多个 HTTP 请求                               │
│ 控制：HTTP 头部 Connection: keep-alive                              │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│                    TCP Keep-Alive                                   │
├─────────────────────────────────────────────────────────────────────┤
│ 层级：传输层                                                        │
│ 作用：检测连接是否存活（心跳检测）                                  │
│ 控制：socket 选项 SO_KEEPALIVE                                      │
│                                                                     │
│ 工作原理：                                                          │
│                                                                     │
│ 客户端                                              服务器          │
│    │                                                   │            │
│    │ ══════════ 正常数据传输 ═══════════════════════   │            │
│    │                                                   │            │
│    │         （空闲 tcp_keepalive_time 秒）            │            │
│    │                                                   │            │
│    │ ── 探测包 ─────────────────────────────────────►  │            │
│    │ ◄─ ACK ─────────────────────────────────────────  │  连接正常  │
│    │                                                   │            │
│    │         （如果无响应，每隔 intvl 秒重试）         │            │
│    │                                                   │            │
│    │ ── 探测包 ─────────────────────────────────────►  │            │
│    │         × 无响应                                  │            │
│    │ ── 探测包 ─────────────────────────────────────►  │            │
│    │         × 无响应                                  │            │
│    │         （probes 次后判定连接失效）               │            │
│    │                                                   │            │
│    │ ══════════ 关闭连接 ═══════════════════════════   │            │
│                                                                     │
│ Linux 参数：                                                        │
│   net.ipv4.tcp_keepalive_time  = 7200  # 空闲 2 小时后开始探测      │
│   net.ipv4.tcp_keepalive_intvl = 75    # 探测间隔 75 秒             │
│   net.ipv4.tcp_keepalive_probes = 9    # 最多探测 9 次              │
│                                                                     │
│ 默认总超时 = 7200 + 75 × 9 = 7875 秒 ≈ 2.2 小时                     │
└─────────────────────────────────────────────────────────────────────┘

两者对比：

┌─────────────┬─────────────────────────┬─────────────────────────────┐
│             │ HTTP Keep-Alive         │ TCP Keep-Alive              │
├─────────────┼─────────────────────────┼─────────────────────────────┤
│ 层级        │ 应用层                  │ 传输层                      │
├─────────────┼─────────────────────────┼─────────────────────────────┤
│ 目的        │ 复用连接，减少握手     │ 检测死连接                  │
├─────────────┼─────────────────────────┼─────────────────────────────┤
│ 默认行为    │ HTTP/1.1 默认开启       │ 默认关闭                    │
├─────────────┼─────────────────────────┼─────────────────────────────┤
│ 超时时间    │ 秒级（如 5-60 秒）      │ 小时级（默认 2 小时）       │
├─────────────┼─────────────────────────┼─────────────────────────────┤
│ 配置方式    │ HTTP 头部               │ socket 选项 + 内核参数      │
└─────────────┴─────────────────────────┴─────────────────────────────┘
```

### 9.4 长连接 vs 短连接对比

```
┌─────────────────────────────────────────────────────────────────────┐
│                         性能对比                                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│ 短连接开销（每次请求）：                                            │
│   TCP 三次握手：1.5 RTT                                             │
│   TLS 握手：2 RTT (TLS 1.2) / 1 RTT (TLS 1.3)                       │
│   数据传输：1 RTT                                                   │
│   TCP 四次挥手：2 RTT                                               │
│   ────────────────────                                              │
│   总计：6.5 RTT (HTTPS + TLS 1.2)                                   │
│                                                                     │
│ 长连接开销（首次 + 后续）：                                         │
│   首次：同短连接                                                    │
│   后续：仅数据传输 1 RTT                                            │
│                                                                     │
│ 假设 RTT = 50ms，10 个请求：                                        │
│   短连接：10 × 6.5 × 50 = 3250 ms                                   │
│   长连接：6.5 × 50 + 9 × 50 = 775 ms                                │
│   节省：76% 时间                                                    │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│                         资源对比                                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│ 短连接：                                                            │
│   优点：                                                            │
│   - 服务器连接数少（用完即释放）                                    │
│   - 无需管理连接状态                                                │
│   - 适合低频请求                                                    │
│                                                                     │
│   缺点：                                                            │
│   - 频繁握手挥手，延迟高                                            │
│   - TCP 慢启动影响吞吐量                                            │
│   - 大量 TIME_WAIT 状态                                             │
│                                                                     │
│ 长连接：                                                            │
│   优点：                                                            │
│   - 减少握手开销，延迟低                                            │
│   - TCP 连接已预热，吞吐量高                                        │
│   - 减少 TIME_WAIT                                                  │
│                                                                     │
│   缺点：                                                            │
│   - 服务器需维护大量连接                                            │
│   - 占用文件描述符和内存                                            │
│   - 需要超时管理                                                    │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

场景选择：

┌─────────────────────────────────────────────────────────────────────┐
│ 使用短连接：                                                        │
│   - 请求频率很低（如每天一次的定时任务）                            │
│   - 服务器资源紧张，无法维护大量连接                                │
│   - 客户端数量巨大，但请求稀疏                                      │
│   - 简单的一次性 API 调用                                           │
├─────────────────────────────────────────────────────────────────────┤
│ 使用长连接：                                                        │
│   - 频繁请求（如网页浏览、API 调用）                                │
│   - 实时通信（如 WebSocket、消息推送）                              │
```

### 9.7 长短连接面试题

**Q16：HTTP 长连接和短连接的区别？**
```
短连接：
- 每次请求建立新 TCP 连接
- 请求完成后立即关闭
- HTTP/1.0 默认行为
- 开销大：每次都要握手/挥手

长连接：
- 一次建立，多次复用
- 超时或主动关闭才断开
- HTTP/1.1 默认行为（Keep-Alive）
- 开销小：减少握手延迟
```

**Q17：HTTP Keep-Alive 和 TCP Keep-Alive 的区别？**
```
HTTP Keep-Alive：
- 应用层概念
- 目的：复用 TCP 连接
- 通过 HTTP 头控制
- 超时通常秒级

TCP Keep-Alive：
- 传输层机制
- 目的：检测死连接（心跳）
- 通过 socket 选项控制
- 超时默认 2 小时
```

**Q18：长连接会导致什么问题？如何解决？**
```
问题：
1. 服务器资源占用（fd、内存）
2. 连接泄漏（忘记关闭）
3. 负载不均衡（连接固定在某台服务器）

解决：
1. 设置合理超时时间
2. 限制最大连接数
3. 使用连接池统一管理
4. 负载均衡器定期重新分配
5. 监控连接状态
```

**Q19：什么场景用短连接？什么场景用长连接？**
```
短连接：
- 请求非常稀疏（每天一次）
- 客户端数量巨大但请求少
- 简单的一次性 API

长连接：
- 频繁请求（网页浏览）
- 实时通信（WebSocket）
- 数据库/缓存访问
- 微服务 RPC
- 低延迟要求
```

**Q20：HTTP/2 为什么只需要一个连接？**
```
多路复用机制：
1. 请求/响应拆分为帧
2. 帧带有流 ID 标识
3. 多个流在单连接上交错传输
4. 接收端根据流 ID 重组

优势：
- 无应用层队头阻塞
- 减少连接管理开销
- 更好的拥塞控制
- 头部压缩跨请求共享
```

## 10. 高级面试题

**Q5：HTTP/2 多路复用如何解决队头阻塞？**
```
应用层解决：
- 请求/响应拆分为帧
- 不同流的帧可以交错传输
- 接收端根据流 ID 重组

但 TCP 层仍存在队头阻塞
```

**Q6：TLS 1.3 比 TLS 1.2 快在哪里？**
```
1. 握手减少到 1-RTT
2. 密钥交换与握手合并
3. 移除复杂密码套件的协商
4. 0-RTT 恢复（使用 PSK）
```

**Q7：如何实现 HTTPS 降级防护？**
```
HSTS (HTTP Strict Transport Security)：
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

- 浏览器强制使用 HTTPS
- 预加载列表内置于浏览器
- 防止中间人 HTTP 降级攻击
```

**Q8：前向保密为什么重要？**
```
场景：攻击者录制所有加密流量

RSA 密钥交换（无前向保密）：
- 服务器私钥泄露后
- 攻击者用私钥解密历史流量中的预主密钥
- 解密所有历史通信

ECDHE（有前向保密）：
- 每次会话使用临时密钥
- 会话结束后临时密钥销毁
- 即使长期私钥泄露，历史通信仍安全
```

**Q9：HTTP/3 为什么选择 UDP？**
```
1. TCP 队头阻塞无法在协议层解决
   - TCP 保证有序交付是内核实现
   - 修改 TCP 需要操作系统升级

2. UDP 是"白纸"
   - 可在用户空间实现可靠传输
   - 流独立，互不阻塞

3. 快速迭代
   - QUIC 在用户空间
   - 不依赖操作系统更新
```

**Q10：Cookie 的 SameSite 属性如何防 CSRF？**
```
CSRF 攻击：
- 用户登录 bank.com，有 Cookie
- 访问恶意网站，触发转账请求
- 浏览器自动携带 bank.com 的 Cookie

SameSite=Strict 防护：
- 跨站请求不携带 Cookie
- 恶意请求无法认证

SameSite=Lax 折中：
- 表单 POST 不携带
- 链接跳转 GET 可携带
- 兼顾安全和用户体验
```
