# 06 - 对比与选型

## 核心概念

Web 实时通信有四种主流方案，选型取决于**通信方向、延迟要求、兼容性和实现复杂度**。

---

## 原理深入

### 四种方案对比

#### 1. 短轮询 (Short Polling)

```
客户端                     服务器
  │ ── GET /messages ────► │  "有新消息吗？"
  │ ◄── 200 [] ────────── │  "没有"
  │      等待 N 秒          │
  │ ── GET /messages ────► │  "有新消息吗？"
  │ ◄── 200 [msg] ──────── │  "有！"
  │      等待 N 秒          │
  │ ── GET /messages ────► │
```

- 客户端定时发 HTTP 请求
- 优点：实现简单，兼容性好
- 缺点：大量无效请求，延迟 = 轮询间隔，服务器压力大

#### 2. 长轮询 (Long Polling)

```
客户端                     服务器
  │ ── GET /messages ────► │  挂起，等有消息才响应
  │      ...等待...         │
  │ ◄── 200 [msg] ──────── │  有消息了！
  │ ── GET /messages ────► │  立即发起下一个
  │      ...等待...         │
```

- 服务器收到请求后不立即响应，等有新数据或超时再返回
- 优点：比短轮询实时，仍基于 HTTP
- 缺点：服务器需维护大量挂起连接，超时重连开销

#### 3. SSE (Server-Sent Events)

```
客户端                     服务器
  │ ── GET /events ──────► │  Content-Type: text/event-stream
  │ ◄── data: msg1 ────── │
  │ ◄── data: msg2 ────── │  服务器持续推送
  │ ◄── data: msg3 ────── │
  │      ...长连接...       │
```

- 基于 HTTP 的单向推送（服务器 → 客户端）
- 优点：原生 API (EventSource)，自动重连，HTTP/2 友好
- 缺点：仅单向，IE 不支持

#### 4. WebSocket

```
客户端 ◄──────────────────► 服务器
       双向全双工实时通信
```

- 独立协议，全双工
- 优点：最低延迟，最小开销，真正双向
- 缺点：需协议升级，代理/firewall 兼容性问题

### 综合对比表

| 维度 | 短轮询 | 长轮询 | SSE | WebSocket |
|------|--------|--------|-----|-----------|
| 通信方向 | 客户端拉 | 客户端拉 | 服务器推 | 双向 |
| 实时性 | 差（间隔级） | 中（秒级） | 好 | 最好（毫秒级） |
| 协议 | HTTP | HTTP | HTTP | WS（HTTP 握手） |
| 服务器压力 | 高（频繁请求） | 中（挂起连接） | 低 | 低 |
| 浏览器兼容 | 全部 | 全部 | 除 IE | 现代浏览器 |
| 自动重连 | 无 | 无 | 原生支持 | 需自行实现 |
| 数据格式 | 任意 | 任意 | 文本 (UTF-8) | 文本 + 二进制 |
| 跨域 | CORS | CORS | CORS | Origin 检查 |

## 选型决策

```
需要实时通信？
    │
    ├─ 否 → REST API (HTTP) 即可
    │
    └─ 是 → 需要客户端发送数据吗？
              │
              ├─ 否 → 只需服务器推送
              │         │
              │         ├─ 简单通知/日志 → SSE
              │         └─ 需要兼容旧浏览器 → 长轮询
              │
              └─ 是 → 需要双向通信
                        │
                        ├─ 高频（聊天/游戏/行情） → WebSocket
                        ├─ 低频（协作文档） → WebSocket 或 SSE + REST
                        └─ 简单场景 → 长轮询（快速原型）
```

### 典型场景

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 聊天室 | WebSocket | 双向高频，低延迟 |
| 股票行情 | WebSocket | 毫秒级推送，二进制帧高效 |
| 新闻/通知推送 | SSE | 单向推送，自动重连 |
| 协同编辑 | WebSocket | 双向操作同步 |
| 文件上传 | HTTP POST | 无需实时，REST 足够 |
| 邮件收件通知 | 长轮询 / SSE | 低频，实现简单 |
| IoT 设备上报 | MQTT / WebSocket | 取决于协议栈 |
| 在线客服 | WebSocket | 双向消息 + 已读回执 |

### REST vs WebSocket

| 维度 | REST (HTTP) | WebSocket |
|------|------------|-----------|
| 模型 | 请求-响应 | 持久连接 + 事件 |
| 适用 | CRUD、查询、文件传输 | 实时推送、聊天、游戏 |
| 缓存 | 支持 HTTP 缓存 | 无缓存 |
| 负载均衡 | 无状态，任意节点 | 需 Sticky 或消息广播 |
| 错误处理 | 标准 HTTP 状态码 | 自定义 Close 码 |
| 调试 | curl/Postman 友好 | 需专用工具 |

**最佳实践**：REST 处理 CRUD 和非实时操作，WebSocket 处理实时事件。二者互补而非替代。

## 常见面试题

**Q1：如何实现一个简单的聊天室？**

```
架构：
  客户端 A ◄── WebSocket ──► 服务器 ◄── WebSocket ──► 客户端 B
                                │
                           消息广播
                           （单节点内存 / 多节点 Redis Pub/Sub）

流程：
1. 客户端 HTTP 登录获取 Token
2. WebSocket 连接时携带 Token 鉴权
3. 发送消息 → 服务器 → 广播给所有在线用户
4. 断线 → 指数退避重连 → 拉取离线消息（HTTP API）
```

**Q2：WebSocket 和 SSE 怎么选？**

- 只需服务器推送（通知、日志、进度条）→ SSE，更简单
- 需要客户端频繁发数据（聊天、游戏操作）→ WebSocket
- SSE 走 HTTP/2 多路复用，防火墙友好；WebSocket 需 Upgrade

**Q3：WebSocket 多服务器怎么广播消息？**

```
方案 1：Sticky Session
  负载均衡按 IP/Session 固定到同一节点

方案 2：消息中间件
  节点 A 收到消息 → Redis Pub/Sub / Kafka → 所有节点 → 推给各自连接的客户端

方案 3：集中式连接管理
  专用 Gateway 管理 WebSocket 连接，业务服务通过 RPC 发消息
```

---

## 实战要点

- 先用 SSE/长轮询快速验证，确认需要双向后再上 WebSocket
- WebSocket 连接数受限于文件描述符和内存，需评估服务器容量
- 移动端注意后台 Kill 后 WebSocket 断连，需配合 Push Notification
- HTTP/3 时代 SSE 因基于 HTTP 可能受益，WebSocket 仍走独立协议
