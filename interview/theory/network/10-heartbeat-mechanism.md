# 10 - 心跳包机制 (Heartbeat Mechanism)

## 简介

心跳包是网络通信中用于检测连接存活状态的机制。不同层级（TCP、HTTP、应用层）都有各自的心跳实现，它们解决不同的问题，不能简单互相替代。

---

## 2. TCP Keep-Alive 详解

### 2.1 工作原理

```
┌─────────────────────────────────────────────────────────────────────┐
│                    TCP Keep-Alive 机制                              │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│ 位置：传输层（内核实现）                                            │
│ 目的：检测 TCP 连接是否还能通信                                     │
│ 默认：关闭                                                          │
│                                                                     │
│ 工作流程：                                                          │
│                                                                     │
│ 客户端                                              服务器          │
│    │                                                   │            │
│    │ ═══════════ 正常数据传输 ════════════════════════ │            │
│    │                                                   │            │
│    │      空闲 tcp_keepalive_time 秒（默认 7200）      │            │
│    │                                                   │            │
│    │ ─── 探测包（无数据，仅 ACK）─────────────────────►│            │
│    │                                                   │            │
│    │ ◄─── ACK ────────────────────────────────────────│ 正常响应   │
│    │                                                   │            │
│    │      连接正常，重置计时器                         │            │
│    │                                                   │            │
│    │ ════════════════════════════════════════════════ │            │
│                                                                     │
│ 异常情况：                                                          │
│                                                                     │
│ 客户端                                              服务器          │
│    │                                                   │            │
│    │ ─── 探测包 ──────────────────────────────────────►│            │
│    │                    × 无响应                       │            │
│    │                                                   │            │
│    │      等待 tcp_keepalive_intvl 秒（默认 75）       │            │
│    │                                                   │            │
│    │ ─── 探测包 ──────────────────────────────────────►│            │
│    │                    × 无响应                       │            │
│    │                                                   │            │
│    │      重复 tcp_keepalive_probes 次（默认 9）       │            │
│    │                                                   │            │
│    │ ─── 探测包 ──────────────────────────────────────►│            │
│    │                    × 无响应                       │            │
│    │                                                   │            │
│    │      判定连接失效，返回 ETIMEDOUT 错误            │            │
│    │      关闭连接                                     │            │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

探测包格式：
┌─────────────────────────────────────────────────────────────────────┐
│ Keep-Alive 探测包特点：                                             │
│                                                                     │
│ - 序列号 = 上次发送的最后一个字节 - 1                               │
│ - 不携带数据                                                        │
│ - 只是为了触发对端的 ACK 响应                                       │
│                                                                     │
│ 正常主机收到后：                                                    │
│   → 发送 ACK（确认当前接收位置）                                    │
│                                                                     │
│ 主机已崩溃/重启：                                                   │
│   → 发送 RST（不认识这个连接）                                      │
│                                                                     │
│ 网络不可达：                                                        │
│   → 无响应（超时后判定失效）                                        │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.2 参数配置

```cpp
// Linux 系统参数（全局）
// /proc/sys/net/ipv4/tcp_keepalive_time  = 7200  // 空闲 2 小时后开始探测
// /proc/sys/net/ipv4/tcp_keepalive_intvl = 75    // 探测间隔 75 秒
// /proc/sys/net/ipv4/tcp_keepalive_probes = 9    // 最多探测 9 次

// 默认检测时间 = 7200 + 75 × 9 = 7875 秒 ≈ 2.2 小时（太慢！）

// Socket 级别配置
int fd = socket(AF_INET, SOCK_STREAM, 0);

// 开启 Keep-Alive
int keepalive = 1;
setsockopt(fd, SOL_SOCKET, SO_KEEPALIVE, &keepalive, sizeof(keepalive));

// 设置空闲时间（Linux 特有）
int keepidle = 60;  // 60 秒后开始探测
setsockopt(fd, IPPROTO_TCP, TCP_KEEPIDLE, &keepidle, sizeof(keepidle));

// 设置探测间隔
int keepintvl = 10;  // 每 10 秒探测一次
setsockopt(fd, IPPROTO_TCP, TCP_KEEPINTVL, &keepintvl, sizeof(keepintvl));

// 设置探测次数
int keepcnt = 3;  // 最多 3 次
setsockopt(fd, IPPROTO_TCP, TCP_KEEPCNT, &keepcnt, sizeof(keepcnt));

// 优化后检测时间 = 60 + 10 × 3 = 90 秒
```

### 2.3 TCP Keep-Alive 的局限性

```
┌─────────────────────────────────────────────────────────────────────┐
│                TCP Keep-Alive 的问题                                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│ 1. 默认时间太长                                                     │
│    - 2 小时后才开始探测                                             │
│    - 对实时性要求高的场景不适用                                     │
│    - 虽然可以调整，但是全局或 socket 级别                           │
│                                                                     │
│ 2. 只检测 TCP 连接层                                                │
│    - 不知道应用层是否正常                                           │
│    - 服务进程可能卡死但 TCP 还在                                    │
│                                                                     │
│    示例：                                                           │
│    ┌──────────────────────────────────────────┐                     │
│    │ 服务器                                    │                     │
│    │   TCP 连接正常 ✓                         │                     │
│    │   HTTP 服务卡死 ×（死锁/资源耗尽）       │                     │
│    │   数据库连接池满 ×                       │                     │
│    │                                          │                     │
│    │   TCP Keep-Alive 检测通过                │                     │
│    │   但实际无法处理业务请求                 │                     │
│    └──────────────────────────────────────────┘                     │
│                                                                     │
│ 3. 某些网络设备可能丢弃                                             │
│    - 某些防火墙/代理不转发 Keep-Alive 包                            │
│    - 导致检测失效                                                   │
│                                                                     │
│ 4. 不携带业务数据                                                   │
│    - 无法做应用级别的健康检查                                       │
│    - 无法传递额外信息                                               │
│                                                                     │
│ 5. 双向检测问题                                                     │
│    - Keep-Alive 需要双方都开启才能互相检测                          │
│    - 只开一方可能检测不完整                                         │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## 3. HTTP Keep-Alive

### 3.1 与 TCP Keep-Alive 的区别

```
┌─────────────────────────────────────────────────────────────────────┐
│          HTTP Keep-Alive vs TCP Keep-Alive                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│ 完全不同的概念！                                                    │
│                                                                     │
│ ┌─────────────────────────────────────────────────────────────┐     │
│ │                    HTTP Keep-Alive                          │     │
│ ├─────────────────────────────────────────────────────────────┤     │
│ │ 层级：应用层（HTTP 协议）                                   │     │
│ │ 目的：复用 TCP 连接，发送多个 HTTP 请求                     │     │
│ │ 控制：HTTP 头部 Connection: keep-alive                      │     │
│ │ 默认：HTTP/1.1 默认开启                                     │     │
│ │ 超时：通常秒级（如 Keep-Alive: timeout=5）                  │     │
│ │ 作用：减少 TCP 握手开销，提升性能                           │     │
│ └─────────────────────────────────────────────────────────────┘     │
│                                                                     │
│ ┌─────────────────────────────────────────────────────────────┐     │
│ │                    TCP Keep-Alive                           │     │
│ ├─────────────────────────────────────────────────────────────┤     │
│ │ 层级：传输层（TCP 协议）                                    │     │
│ │ 目的：检测连接是否存活                                      │     │
│ │ 控制：socket 选项 SO_KEEPALIVE                              │     │
│ │ 默认：关闭                                                  │     │
│ │ 超时：通常小时级（默认 2 小时）                             │     │
│ │ 作用：发现死连接，释放资源                                  │     │
│ └─────────────────────────────────────────────────────────────┘     │
│                                                                     │
│ 关系：                                                              │
│   - HTTP Keep-Alive 复用的 TCP 连接可以开启 TCP Keep-Alive          │
│   - 两者解决不同问题，可以同时使用                                  │
│   - HTTP Keep-Alive 是"连接复用"                                    │
│   - TCP Keep-Alive 是"存活检测"                                     │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.2 HTTP 层超时机制

```
HTTP 服务器通常有多种超时设置：

┌─────────────────────────────────────────────────────────────────────┐
│                    Nginx 超时配置示例                               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│ # 客户端连接相关                                                    │
│ keepalive_timeout 65;           # 空闲连接保持时间                  │
│ keepalive_requests 100;         # 单连接最大请求数                  │
│                                                                     │
│ # 读取超时                                                          │
│ client_header_timeout 60;       # 读取请求头超时                    │
│ client_body_timeout 60;         # 读取请求体超时                    │
│                                                                     │
│ # 发送超时                                                          │
│ send_timeout 60;                # 发送响应超时                      │
│                                                                     │
│ # 与上游连接                                                        │
│ proxy_connect_timeout 60;       # 连接上游超时                      │
│ proxy_read_timeout 60;          # 读取上游响应超时                  │
│ proxy_send_timeout 60;          # 发送到上游超时                    │
│                                                                     │

这些超时不是"心跳"，而是"操作超时"：
  - 在规定时间内没有完成操作，则断开连接
  - 不是周期性探测
```

### 4.3 心跳包设计示例

```cpp
// 心跳消息结构
struct HeartbeatMessage {
    uint32_t type;        // 消息类型：PING=1, PONG=2
    uint64_t timestamp;   // 发送时间戳
    uint32_t sequence;    // 序列号
    uint32_t payload_len; // 扩展数据长度
    // 可选：负载信息、服务状态等
};

// 客户端心跳逻辑
class HeartbeatClient {
private:
    int heartbeat_interval_ = 30;   // 心跳间隔（秒）
    int heartbeat_timeout_ = 10;    // 响应超时（秒）
    int max_missed_ = 3;            // 最大丢失次数
    int missed_count_ = 0;          // 当前丢失计数
    uint32_t sequence_ = 0;

public:
    void Start() {
        // 定时器：每 heartbeat_interval_ 秒发送心跳
        timer_.Start(heartbeat_interval_, [this]() {
            SendPing();
        });
    }

    void SendPing() {
        HeartbeatMessage msg;
        msg.type = PING;
        msg.timestamp = GetCurrentTimeMs();
        msg.sequence = ++sequence_;

        Send(msg);

        // 启动超时定时器
        timeout_timer_.Start(heartbeat_timeout_, [this]() {
            OnTimeout();
        });
    }

    void OnPongReceived(const HeartbeatMessage& pong) {
        timeout_timer_.Cancel();
        missed_count_ = 0;

        // 计算延迟
        uint64_t rtt = GetCurrentTimeMs() - pong.timestamp;
        UpdateLatency(rtt);
    }

    void OnTimeout() {
        missed_count_++;
        if (missed_count_ >= max_missed_) {
            // 连接失效
            OnConnectionLost();
        }
    }
};

// 服务端心跳逻辑
class HeartbeatServer {
private:
    int idle_timeout_ = 90;  // 空闲超时（秒）

public:
    void OnPingReceived(const HeartbeatMessage& ping) {
        // 重置空闲计时器
        idle_timer_.Reset();

        // 立即回复 PONG
        HeartbeatMessage pong;
        pong.type = PONG;
        pong.timestamp = ping.timestamp;  // 回传时间戳
        pong.sequence = ping.sequence;

        // 可选：添加服务状态
        AddServerStatus(pong);

        Send(pong);
    }

    void OnIdleTimeout() {
        // 客户端长时间没有心跳，关闭连接
        CloseConnection();
    }
};
```

## 6. 心跳与 NAT/防火墙

### 6.1 NAT 超时问题

```
┌─────────────────────────────────────────────────────────────────────┐
│                    NAT 超时问题详解                                 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│ NAT 设备维护连接映射表：                                            │
│                                                                     │
│ ┌─────────────────────────────────────────────────────────────┐     │
│ │ 内网 IP:Port      │ 外网 IP:Port      │ 目标 IP:Port        │     │
│ ├───────────────────┼───────────────────┼─────────────────────┤     │
│ │ 192.168.1.10:5000 │ 1.2.3.4:40000     │ 5.6.7.8:80          │     │
│ │ 192.168.1.11:6000 │ 1.2.3.4:40001     │ 5.6.7.8:443         │     │
│ └─────────────────────────────────────────────────────────────┘     │
│                                                                     │
│ 超时机制：                                                          │
│   - TCP 连接：通常 5-30 分钟无数据则删除映射                        │
│   - UDP 连接：通常 30-60 秒无数据则删除映射                         │
│   - 不同设备超时时间不同                                            │
│                                                                     │
│ 问题场景：                                                          │
│                                                                     │
│ 客户端          NAT 设备                            服务器          │
│    │               │                                   │            │
│    │ ═══ TCP ═════►│═══════════════════════════════►   │            │
│    │               │                                   │            │
│    │          长时间无数据（如 10 分钟）               │            │
│    │          NAT 映射超时删除                         │            │
│    │               │                                   │            │
│    │ ─── 数据 ────►│ × 找不到映射，丢弃               │            │
│    │               │                                   │            │
│    │   客户端认为连接还在                              │            │
│    │   服务器等待数据                                  │            │
│    │   双方都不知道出了问题                            │            │
│                                                                     │
│ 解决方案：                                                          │
│   - 定期发送心跳，刷新 NAT 映射                                     │
│   - 心跳间隔 < NAT 超时时间                                         │
│   - 通常设置 30-60 秒                                               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## 7. 面试深度问题

**Q1：为什么 TCP 有 Keep-Alive 还需要应用层心跳？**
```
核心区别：检测层级不同

TCP Keep-Alive：
- 只检测"TCP 连接是否通"
- 内核级别响应，不涉及应用层
- 服务进程卡死，TCP 还能响应

应用层心跳：
- 检测"服务是否能正常处理请求"
- 需要应用层处理并响应
- 能发现服务假死

典型场景：
  服务器数据库连接池满，无法处理请求
  - TCP Keep-Alive：正常 ✓（内核响应）
  - 应用层心跳：超时 ×（应用无法响应）
```

**Q2：TCP Keep-Alive 默认为什么是 2 小时？**
```
历史原因：
- RFC 1122 建议不少于 2 小时
- 假设是"长连接"场景
- 减少网络开销

现代问题：
- NAT 超时通常 5-30 分钟
- 高可用要求快速检测
- 2 小时太长不实用

实践：
- 调整为 60 秒左右
- 配合应用层心跳使用
```

**Q3：心跳间隔如何设置？**
```
考虑因素：
1. NAT 超时时间（通常 5-30 分钟）
2. 故障检测速度需求
3. 网络带宽和服务器负载
4. 客户端电量消耗（移动端）

常见配置：
- 服务端通信：30-60 秒
- 移动端 IM：1-5 分钟（自适应）
- 游戏场景：1-5 秒（低延迟要求）

公式参考：
  心跳间隔 < NAT 超时时间 / 2
  检测时间 = 心跳间隔 × 最大丢失次数
```

**Q4：心跳失败后如何处理？**
```
处理策略：

1. 重试机制
   - 不要一次失败就断开
   - 通常重试 2-3 次
   - 可以逐步缩短间隔

2. 重连策略
   - 指数退避：1s, 2s, 4s, 8s...
   - 最大重连间隔：如 60 秒
   - 添加随机抖动，避免惊群

3. 通知上层
   - 更新连接状态
   - 触发故障转移
   - 显示用户提示

4. 资源清理
   - 关闭失效连接
   - 释放相关资源
```

**Q5：如何检测服务"假死"？**
```
假死定义：
  进程存活，但无法正常处理请求

检测方法：

1. 应用层心跳必须穿透业务逻辑
   // 错误：在网络层回复
   if (isPing) return pong;  // 不经过业务

   // 正确：放入业务队列处理
   businessQueue.put(pingMessage);  // 经过业务线程

2. 心跳处理加超时
   // 心跳请求在业务线程执行
   // 如果业务线程卡死，心跳也会超时

3. 健康检查端点
   GET /health
   {
     "status": "ok",
     "db": "ok",
     "cache": "ok",
     "queue_size": 10
   }
```

**Q6：WebSocket 为什么需要单独的 Ping/Pong？**
```
原因：

1. 应用层协议独立性
   - WebSocket 可以运行在 HTTP 代理之后
   - 代理可能不透传 TCP Keep-Alive

2. 更快的检测
   - 可以自定义间隔
   - 协议内置支持

3. 穿透中间件
   - Nginx 等代理可以识别 WebSocket Ping
   - 不会被当作异常数据

4. 双向支持
   - 客户端可以发 Ping
   - 服务端也可以发 Ping
   - 灵活控制
```

**Q7：为什么说"只用 TCP Keep-Alive 不行，但可以只用应用层心跳"？**
```
TCP Keep-Alive 不足：
- 只检测网络层
- 不检测应用层
- 无法检测服务假死

应用层心跳可以：
- 检测应用层状态
- 顺带检测网络层（网络断了，心跳也会超时）
- 可携带业务数据

但应用层心跳的代价：
- 需要自己实现
- 消息体更大
- 占用应用层资源

最佳实践：
- 两者配合使用
- TCP Keep-Alive 作为兜底
- 应用层心跳做主要检测
```

**Q8：长连接服务如何设计心跳？**
```
完整设计：

1. 协议设计
   struct Heartbeat {
       uint8_t  type;       // PING=1, PONG=2
       uint64_t timestamp;  // 时间戳
       uint32_t seq;        // 序列号
   };

2. 客户端逻辑
   - 定时发送 PING（如 30 秒）
   - 等待 PONG（超时如 5 秒）
   - 连续 3 次超时则重连

3. 服务端逻辑
   - 收到 PING 立即回复 PONG
   - 检测客户端空闲时间
   - 超时则主动断开（如 90 秒）

4. 空闲检测优化
   - 有业务数据时重置计时器
   - 只在空闲时发心跳
   - 减少不必要流量

5. 监控指标
   - 心跳延迟（RTT）
   - 心跳丢失率
   - 重连次数
```
